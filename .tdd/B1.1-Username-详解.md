## 1. 动手前先搞懂三个概念

不然表上的字你也只是照着抄，不知道为什么。

### 1.1 什么是「值对象」

`Username` 不是「一个装了字符串的盒子」，它是**一个自带规则的用户名**。区别在于：

| | 普通 String | 值对象 `Username` |
|---|---|---|
| 能不能是 null | 能 | **不能**，构造就拦住 |
| 能不能是 `"   "` | 能 | **不能** |
| 能不能是 `"abc"`（太短） | 能 | **不能** |
| 能不能拿 `"zhanghao"` 当用户名 | 能 | 能 |

所以这 10 条测试里，**前 8 条在定义「什么样的字符串才算一个合法用户名」**，后 2 条在定义「两个 `Username` 什么时候算同一个」。

这就是为什么值对象是练 TDD 的最佳起点：**规则全在这个类里面，外面什么都不用管。**

### 1.2 第 1 条为什么要强调「不是 `NullPointerException`」

这是整张表里最容易被忽略、但最值钱的一条。

如果你在构造方法里**不检查 null**，直接写：

```java
this.value = value.trim();     // value 是 null 时 → 这里会抛 NullPointerException
```

那么 `new Username(null)` 确实**会**抛异常 —— 抛的是 NPE。

⚠️ 这时候如果测试只写「断言抛异常」，**它会绿**，但你的代码是错的：

- `new Username(null)` 抛 `NullPointerException` → 说明是「我没想到会传 null，代码崩了」
- `new Username(null)` 抛 `IllegalArgumentException` → 说明是「我明确知道不允许 null，我主动拒绝了」

前者到了 web 层会变成 **HTTP 500 服务器错误**（用户看到"系统异常"）；后者才是 **400 参数错误**（用户看到"用户名不能为空"）。

**所以断言必须写到"是哪一类异常"这一层**，这就是表里第 1 行特意加粗的原因。

### 1.3 为什么每条都要先看红

TDD 有个绕不开的动作：**在写实现之前，先亲眼看到测试失败。**

原因不是仪式感。是因为一个"永远会绿"的测试等于**没有测试**，而你没看到过它红，就永远不知道它是不是那种测试。举个真会发生的例子：

> 第 5 条写 `assertThat(new Username("abcd").value()).isEqualTo("abcd")`。
> 这条**在你还没写任何长度校验的时候就是绿的**（因为 "abcd" 本来就能通过）。
> 它绿，不代表你实现了长度上限；它只是**守住**了下边界是"闭区间"（4 位合法，不是 5 位才合法）。

看到红，你才知道这条测试到底在钉什么。看到绿，你要问自己一句：**"它是被我实现的，还是本来就绿的？"**

### 1.4 拆开看 `assertThatThrownBy(() -> new Username(null))`

这行是整份文档里第一处"看着不像 Java"的代码，先拆开：

```java
assertThatThrownBy(() -> new Username(null))          // ① 入口 + ② 待测代码（lambda）
        .isInstanceOf(IllegalArgumentException.class); // ③ 断言：异常类型
```

**① `assertThatThrownBy(...)`** —— AssertJ 提供的"断言抛出异常"入口。
它需要一个 `ThrowingCallable`（可以理解成"一段还没执行的代码"），然后**由它去执行、并捕获异常**。

**② `() -> new Username(null)` —— lambda，即"把一段代码打包成对象"**

为什么不能直接写 `assertThatThrownBy(new Username(null))`？

> 因为 Java 是**立即求值**的：写 `new Username(null)` 的那一刻，构造方法**立刻就被执行了**，
> 异常会在"调用 `assertThatThrownBy` 之前"抛出来 —— AssertJ 连碰都没碰到，谈何断言？

lambda `() -> xxx` 的作用是：**不现在执行，而是把这段代码本身当作值传过去**。
至于什么时候执行、异常怎么接住，由 AssertJ 决定。这就是它有资格说"我期望这段代码抛异常"的前提。

**③ `.isInstanceOf(IllegalArgumentException.class)`** —— 断言"抛出来的异常类型是 IAE"。
`.class` 是 Java 的**类字面量**：`IllegalArgumentException.class` 表示"这个类型本身"，
类型是 `Class<IllegalArgumentException>`。测试里凡是"要传一个类型进去"的地方，都是这个写法。

**为什么链式换行**（第二行缩进多 8 格）：AssertJ 是流式 API，一个断言链可能很长。
按"每个 `.方法()` 独占一行、比上一级多缩进一层"写，出错的环节一眼可见。
这跟 `.hasMessageContaining("用户名")` 叠成三行是同一回事。

**顺带认识另一种写法**（JUnit 5 自带的，你以后会在别处看到）：

| | AssertJ | JUnit 5 |
|---|---|---|
| 写法 | `assertThatThrownBy(() -> ...).isInstanceOf(X.class)` | `assertThrows(X.class, () -> ...)` |
| 异常类型的位置 | 链式方法里 | **第二个参数之后** |
| 附加断言 | `.hasMessageContaining("...")` 直接续写 | 需要 `e.getMessage()` 自己判断 |

两者都行。本模块统一用 AssertJ，因为**提示信息（`.hasMessageContaining`）能直接续在链上**，
这正是登录需求里「三种失败要给不同提示」要频繁断言的东西。

### 1.5 代码里那些灰色小字不是你的代码

在 IDEA 里你会看到这行后面多出一截灰色字，比如：

```java
new Username( value: "abc")                  // ← value: 是参数名提示
AbstractThrowableAssert<capture of ?, capture of ?>   // ← 悬停时的类型提示
```

**这两样都不是你写的代码，也不在文件里**：

| 现象 | 是什么 | 要不要管 |
|---|---|---|
| `value:` / `description:` | IDEA 的**参数名提示**（inlay hint），把形参名浮在实参前面，帮你认参数顺序 | 不用管。想关掉：`Settings → Editor → Inlay Hints → Java → Parameter names` |
| `AbstractThrowableAssert<capture of ?, capture of ?>` | 鼠标悬停时的**类型提示**，显示这条链的返回类型；`capture of ?` 是泛型通配符的"捕获类型"，是编译器在描述自己算出来的类型 | 不用管，跟你的测试逻辑无关 |

> **判断方法**：把光标移到那行按 `Home`/`End` 走一遍 —— 光标**不会**停在灰色字上，就说明它不是文件内容。

### 1.6 把它记成一个模板（可以背下来的那种）

上面那行确实可以当成**固定三段式**来记：

```java
assertThatThrownBy( ① 一段"会抛异常"的代码 )
        .isInstanceOf( ② 异常类型.class )
        .hasMessageContaining( ③ 提示里的片段 );   // ③ 可省
```

| 空位 | 填什么 | 关键约束 |
|---|---|---|
| ① | **无参** lambda：`() -> 你的代码` | 必须是 `() -> ...` 形式。AssertJ 只负责"替你把这段代码调用一次，并把抛出的异常接住"，所以它不能给这段代码传参数、也不关心返回值 |
| ② | `XxxException.class` | 是**类字面量**，不是字符串。写 `"IllegalArgumentException"` 编译不过 |
| ③ | 提示文案的片段（可选） | `.hasMessageContaining("用户名")` 是**子串匹配**（含这三个字就行）；`.hasMessage("用户名不能为空")` 是**一字不差** |

**每个空位对应的其实是一条断言意图**，正好和需求一一对应：

| 空位 | 回答的问题 |
|---|---|
| ① | 「**哪段代码**该抛异常？」 |
| ② | 「抛的是**哪一类**异常？」（参数非法 → IAE；业务失败 → 自定义异常） |
| ③ | 「提示**说清楚了**吗？」（登录需求要求三种失败给三种不同提示，全靠这一条钉） |

**两个容易搞混的点**：

1. **`.hasMessageContaining` vs `.hasMessage`**：前者是包含（松），后者是全等（紧）。
   本模块统一用 `Containing` —— 因为提示文案以后可能微调（"不能为空" → "不能为空，请重新输入"），
   子串匹配不会因为这种改动就红。**代价是更松**：写 `Containing("用户")` 就太弱了，别退化成那样。
2. **一次 `assertThatThrownBy` 只对应"一次抛出"**。要测三个不同的坏输入，就写三遍（见第 7 条）。

**什么时候不要用它**：只在"期望代码抛异常"时用。断言**正常返回值**要用另一个入口：

```java
assertThat( new Username("abcd").value() ).isEqualTo("abcd");   // 没有异常，用 assertThat
```

> 一句话口诀：**`assertThat` 断言"值"，`assertThatThrownBy` 断言"抛"。**

## 2. 第 0 轮：先把测试类的骨架子敲好

打开你已经建好的 `UsernameTest.java`，把它改成这样（**先只写骨架，一个 `@Test` 都不写**）：

```java
package com.mall.auth.domain.model;

import org.junit.jupiter.api.DisplayName;
import org.junit.jupiter.api.Test;

import static org.assertj.core.api.Assertions.assertThat;
import static org.assertj.core.api.Assertions.assertThatThrownBy;

@DisplayName("Username 值对象")
class UsernameTest {

    // ↓↓↓ 类的身体从这里开始，所有方法都写在下面这个大括号里 ↓↓↓

    // 10 个 @Test 方法，接下来一条一条往里加

    private static String repeat(char c, int times) {
        StringBuilder sb = new StringBuilder(times);
        for (int i = 0; i < times; i++) {
            sb.append(c);
        }
        return sb.toString();
    }

    // ↑↑↑ 类的身体到这里结束 ↑↑↑
}
```

⚠️ **最容易踩的坑：`repeat` 必须写在类的 `{}` 里面。** 如果你看到 IDEA 报
`class, interface, enum, or record expected`，几乎一定是类的 `}` 提前闭合了 ——
Java 不允许"方法长在类外面"。把方法移到类的 `}` 之前即可。

> **一句话规则**：文件里**最后一个 `}` —— 且只有最后一个 —— 是用来关类的**。
> 所以每加一个新方法，都插到"最后一个 `}` 的**前面**"，**不要贴在文件末尾**。
>
> **IDEA 自查动作**：把光标点在第 8 行那个 `{` 上，IDEA 会高亮它配对的那个 `}`。
> 高亮到**文件最后那个 `}`** → 对；高亮到**中间的**某个 `}` → 就是这个 `}` 放错了位置。
> （也可以按 `Ctrl+Alt+L` 格式化，缩进一下子错位的地方会很显眼。）

### 2.1 缩进：一键对齐，顺便当结构探针

粘贴代码时缩进经常会乱（IDEA **不会**修正粘贴进来的缩进，只在回车换行时自动对齐）。
打开文件按一下：

```
Ctrl + Alt + L        （菜单：Code → Reformat Code）
```

**缩进阶梯**（Java 通用约定 = 每层 4 空格，也是 IDEA 默认）：

| 列 | 放什么 |
|---|---|
| 0 | `package`、`import`、类声明、类上的注解 |
| 4 | 类成员：字段、方法（以及方法的 `@Test` / `@DisplayName` 注解） |
| 8 | 方法体里的语句 |
| 12 | `for` / `if` 里面的语句 |
| 16 | 链式调用的续行（AssertJ 那串 `.isInstanceOf(...)`） |

> **为什么值得在意**（不是因为好看）：Java 编译器**完全不在乎缩进**，乱着也能跑。
> 但 **缩进是发现「花括号放错位置」的第一道防线** ——
> 如果 `@Test` 方法被关在类外面，它的缩进会**明显比同类方法少一层**，
> 一眼就能看出来。缩进乱了，这类结构错误就被藏起来了。
> IDEA 左侧有**缩进参考竖线**，对不上就是结构有问题。

两点说明：

- 类前面写的是 `class`（不是 `public class`）—— JUnit 5 不要求 public，这样也能避免 IDEA 提示"类名和文件名"以外的干扰。
- 你现在的文件是 `public class UsernameTest`，改成 `class` 就行；忘了改也**不影响运行**，只是 IDEA 会提示一句。
- `import static ...assertThatThrownBy` 就是表里第 1~4、7 条要用的那个「断言抛异常」的工具；`assertThat` 是剩下几条用的。

> 手册 5.1 节里用的是 `@Nested` 分组写法（创建 / 值语义 两组）。**两种都可以，但请二选一，别混用**。本文统一用最简单的扁平写法 —— 因为方法名里已经带了 `when_xxx` 前提，不需要再分组，而且扁平写法下 `-Dtest=UsernameTest#方法名` 一定跑得起来。

### 顺手加一个小工具（Java 8 没有 `String.repeat`）

第 4、6 条要造"长度 21"和"长度 20"的字符串，Java 8 没有 `"a".repeat(21)`。在测试类里加一个私有方法：

```java
private static String repeat(char c, int times) {

    for (int i = 0; i < times; i++) {
        sb.append(c);
    }
    return sb.toString();

```

放在类里，`@Test` 方法外面。后面所有测试都用它，别手敲 21 个 a。

### 第 1 条 · `should_reject_when_username_is_null`

**它在钉什么**：`null` 必须被**主动拒绝**，抛 `IllegalArgumentException`，不许漏成 NPE。

**① 写测试**

```java
@Test
@DisplayName("用户名为 null → 抛 IllegalArgumentException（不是 NullPointerException）")
void should_reject_when_username_is_null() {
    assertThatThrownBy(() -> new Username(null))
            .isInstanceOf(IllegalArgumentException.class);
}
```

- `assertThatThrownBy(() -> ...)` 里的 `() -> new Username(null)` 是 **lambda**（延迟执行的一段代码）。AssertJ 会去执行它，然后检查"抛出的异常是不是 IAE"。
- 注意这里**故意没有** `.hasMessageContaining(...)` —— 第 2 条才管提示文案，这一条只管**异常类型**。一次只钉一件事。

**② 跑 → 第一次红是「编译红」**

```text
[ERROR] .../UsernameTest.java:[13,38] 找不到符号
  符号:   类 Username
[INFO] BUILD FAILURE
```

⚠️ 这里**没有** `Tests run:` 这一行。这是**编译红** —— 测试类引用了还不存在的 `Username` 类，压根没编译过，Surefire 没机会跑任何用例。看到这个不要慌，这是 TDD 的正常第一步。

**③ 补最小生产代码，让它能编译**

新建 `mall-auth/src/main/java/com/mall/auth/domain/model/Username.java`：

```java
package com.mall.auth.domain.model;

/** 用户名值对象。TDD 第 1 步：先写空壳让测试能编译，校验逻辑故意还没写。 */
public final class Username {

    private final String value;

    public Username(String value) {
        this.value = value;          // ← 故意不校验，等着测试催
    }

    public String value() {
        return value;
    }
}
```

> ⚠️ **空壳 ≠ 空类。** 只写 `public class Username {}`（里面什么都不放）不是空壳，是**空类** ——
> 那样 Java 只会给它一个隐式无参构造 `Username()`，测试里的 `new Username(null)` 直接报
> `无法将类 Username 中的构造器 Username 应用到给定类型 / 需要: 没有参数`。
> **三件套一个都不能少**：`private final String value;` 字段 + `public Username(String value)` 构造 + `public String value()` 取值。
> 「空壳」的意思是**没有校验逻辑**，不是**没有内容**。

**④ 再跑 → 现在是「断言红」**

```text
[ERROR] UsernameTest.should_reject_when_username_is_null
[ERROR]   Expecting code to raise a throwable.
[INFO] Tests run: 1, Failures: 1, Errors: 0, Skipped: 0
[INFO] BUILD FAILURE
```

✅ **这才是标准的 TDD 红**：`Tests run: 1, Failures: 1` + `Expecting code to raise a throwable`（"我期望这段代码抛异常，它却没抛"）。

**⑤ 补实现 → 绿**

⚠️ **此刻最容易走偏的地方**：看着 `Username` 里那么多没实现的东西（长度、字符集、trim），你会很想一次全写进去。**别写。**

| 现在写 | 后果 |
|---|---|
| 只加 null 检查 | 第 2 条（`"   "`）会红 → 再补 blank 检查 → 第 3 条会红 → …**每一行代码都是被一条测试催出来的** |
| 一次把 10 条全实现 | 第 2~10 条**全是绿的**，你永远不知道哪一行是为了哪条需求写的；将来规则要改，也不知道动哪里安全 |

「一次只让一条用例从红变绿」是 TDD 里唯一不能松的纪律。左列那种写法看着"笨"，换来的是**每一行生产代码都能说出对应哪条测试**。

在构造方法里加 null 检查：

```java
public Username(String value) {
    if (value == null) {
        throw new IllegalArgumentException("用户名不能为空");
    }
    this.value = value;
}
```

再跑：

```text
[INFO] Tests run: 1, Failures: 0, Errors: 0, Skipped: 0
[INFO] BUILD SUCCESS
```

→ 第 1 条完成。

> **为什么判断顺序必须是"先 null 再 trim"**：`value.trim()` 遇到 null 就炸。所以 null 检查必须写在所有对 `value` 取值的前面。这个顺序你以后每次都会遇到。

### 第 2 条 · `should_reject_when_username_is_blank`

**它在钉什么**：全是空格的 `"   "` 也必须被拒，而且**提示文案里要有"用户名"**（方便前端直接显示给用户）。

**① 写测试**

```java
@Test
@DisplayName("用户名全是空格 → 抛 IllegalArgumentException，提示含「用户名」")
void should_reject_when_username_is_blank() {
    assertThatThrownBy(() -> new Username("   "))
            .isInstanceOf(IllegalArgumentException.class)
            .hasMessageContaining("用户名");
}
```

**② 跑 → 断言红**

`"   "` 不是 null，第 1 轮的 null 检查拦不住它 → 没抛异常 →

```text
[INFO] Tests run: 1, Failures: 1
[ERROR]   Expecting code to raise a throwable.
```

**③ 补实现 → 绿**（把条件从"是不是 null"扩成"是不是没内容"）

⚠️ **注意是"改条件"，不是"再加一个 if"。** 常见错法（并排加第二个 if）：

```java
if (value == null) {                                  // ← 这个要删掉
    throw new IllegalArgumentException("用户名不能为空");
}
if (value == null || value.trim().isEmpty()) {        // ← 只留这一个
    throw new IllegalArgumentException("用户名不能为空");
}
```

这样写**功能是对的、测试会绿**，但 IDEA 会把第二个 if 里的 `value == null` 标黄：
`Condition 'value == null' is always 'false'`（第一个 if 已经把它抛掉了，这里永远走不到）。

**为什么必须删掉第一个**：那半句是**死条件** —— 看起来像在防御 null，其实拦不到任何东西，
读代码的人会误以为 null 是从这里被拒的；而且两处 `throw` 文案重复，改提示语要改两处。

正确形态（一个 if 收掉）：

```java
if (value == null || value.trim().isEmpty()) {
    throw new IllegalArgumentException("用户名不能为空");
}
```

> 删冗余分支这件事**不影响行为**，正是手册 5.5 节说的「重构」：测试全绿前提下调整结构，改完再跑一次，必须仍然全绿。
> **黄色警告不影响编译和运行**，它只是 IDEA 在提醒你该重构了。想知道具体是哪条提示，把鼠标停在黄色波浪线上，或按 `Alt+Enter` 看它给的一键修复。

```java
if (value == null || value.trim().isEmpty()) {
    throw new IllegalArgumentException("用户名不能为空");
}
```

**④ 跑 → 绿**

> **两个细节**：
> 1. `value.trim().isEmpty()` 不能用 `value.isEmpty()` —— `"   ".isEmpty()` 是 `false`。
> 2. 这里**只加了校验，没有改 `this.value = value`**。也就是说此刻 `new Username("  zhanghao  ")` 的 `value()` 返回的还是**带空格的原始串** —— 这是故意的，改它（trim 归一化）是第 8 条的事。**一次只改一件事**，测试才好定位。

### 第 3 条 · `should_reject_when_length_is_3`

**它在钉什么**：长度下限是 4，**3 位必须拒**。

**① 写测试**

```java
@Test
@DisplayName("用户名长度 3 → 抛 IllegalArgumentException")
void should_reject_when_length_is_3() {
    assertThatThrownBy(() -> new Username("abc"))
            .isInstanceOf(IllegalArgumentException.class);
}
```

**② 跑 → 断言红**（"abc" 有内容、不是 null，前两条拦不住它）

**③ 补实现 → 绿**（先加常量，再加判断）

```java
private static final int MIN_LENGTH = 4;

public Username(String value) {
    if (value == null || value.trim().isEmpty()) {
        throw new IllegalArgumentException("用户名不能为空");
    }
    if (value.trim().length() < MIN_LENGTH) {
        throw new IllegalArgumentException("用户名长度不能少于 " + MIN_LENGTH + " 位");
    }
    this.value = value;
}
```

**④ 跑 → 绿**

> **常量为什么现在就抽**：值 4 会在后面好几条里复用，也会出现在错误提示里。硬编码 `4` 是典型的"实现细节漏进多处"。抽常量**不算提前设计**，它就是这一条测试要用的东西。`MAX_LENGTH = 20` 下一轮再抽 —— **别一次把两个都写上**，那是给未来的测试写实现。

### 第 4 条 · `should_reject_when_length_is_21`

**它在钉什么**：长度上限是 20，**21 位必须拒**。

**① 写测试**（用上面那个 `repeat` 小工具）

```java
@Test
@DisplayName("用户名长度 21 → 抛 IllegalArgumentException")
void should_reject_when_length_is_21() {
    assertThatThrownBy(() -> new Username(repeat('a', 21)))
            .isInstanceOf(IllegalArgumentException.class);
}
```

**② 跑 → 断言红**（现在没有上限判断，21 个 a 直接过了）

**③ 补实现 → 绿**

```java
private static final int MAX_LENGTH = 20;

// 在 MIN_LENGTH 判断之后追加：
if (value.trim().length() > MAX_LENGTH) {
    throw new IllegalArgumentException("用户名长度不能超过 " + MAX_LENGTH + " 位");
}
```

**④ 跑 → 绿**

> **为什么是 3 和 21，不是 2 和 30**：这是**边界值分析**。规则是「4 ≤ 长度 ≤ 20」，
> 那真正容易写错的就是**边界两侧的那一格** —— 3 和 4、20 和 21。
> 拿 `"a"`（长度 1）去测当然也红，但它红得没信息量：把边界写成 `< 10` 它照样红，你发现不了 bug。
> **测边界，不测中间。**

### 第 5 条 · `should_accept_when_length_is_4`

**它在钉什么**：4 位是**合法的**（下边界是闭区间）。

**① 写测试**

```java
@Test
@DisplayName("用户名长度 4 → 创建成功，value() 等于 abcd")

    assertThat(new Username("abcd").value()).isEqualTo("abcd");

```

**② 跑 → 这次大概直接绿**

不用惊讶 —— 第 3 条已经把 `< 4` 拦掉了，所以 4 位天然放行。**但这条测试必须存在**，因为它拦的是另一个方向的错：

> 假设哪天你把 `length() < MIN_LENGTH` 手滑写成 `length() <= MIN_LENGTH`，
> 第 3 条（长度 3）**照样绿**，只有第 5 条会红。

**每一条边界都要有"内侧"和"外侧"两个测试**，只测外侧等于只锁了一半的门。

**③ 什么都不用改，绿了 → 下一条。**

### 第 7 条 · `should_reject_when_charset_is_invalid`

**它在钉什么**：只允许字母、数字、下划线。空格、中文、`@` 都不行。

**① 写测试**

```java
@Test
@DisplayName("用户名含非法字符 → 抛 IllegalArgumentException")
void should_reject_when_charset_is_invalid() {
    assertThatThrownBy(() -> new Username("zhang hao"))
            .isInstanceOf(IllegalArgumentException.class);
    assertThatThrownBy(() -> new Username("张三张三"))
            .isInstanceOf(IllegalArgumentException.class);
    assertThatThrownBy(() -> new Username("zh@ng"))
            .isInstanceOf(IllegalArgumentException.class);
}
```

⚠️ **这里有个必须知道的坑 —— 表里写的是 `"张三"`，请改成 `"张三张三"`。**

原因：`"张三"` 在 Java 里 `.length()` 是 **2**，它会被第 3 条的**长度规则**先拦掉。这时这条测试**会绿**，但绿得毫无意义 —— 你那个字符集校验根本没被验证过，删掉字符集校验它也照样绿。这就是"假绿"。

好的测试数据要**只违反一条规则**：
- `"张三张三"` 长度 4（过长度关），只有字符集违规 ✅
- `"zhang hao"` 长度 9（过长度关），只有字符集违规（中间有空格，trim 去不掉）✅
- `"zh@ng"` 长度 5（过长度关），只有字符集违规 ✅

**② 跑 → 断言红**（三条都会红，因为现在完全没有字符集判断）

**③ 补实现 → 绿**

```java
private static final String ALLOWED_PATTERN = "^[A-Za-z0-9_]+$";

// 在长度上限判断之后追加：
if (!value.trim().matches(ALLOWED_PATTERN)) {
    throw new IllegalArgumentException("用户名只能包含字母、数字和下划线");
}
```

**④ 跑 → 绿**

> **正则 `^[A-Za-z0-9_]+$` 拆给你看**：
> `^` 开头，`$` 结尾，中间 `[A-Za-z0-9_]` 是允许的字符集，`+` 表示"一个或多个"。
> 加上 `^...$` 才能保证**整串**都合规 —— 少了它，`matches()` 仍然要求全匹配（Java 的 `matches` 本身就是全匹配），但写上更容易读，也避免以后换成 `find()` 时踩坑。
> **注意这里用的是 `trim()` 之后的串**：`" zhanghao "` 中间没有空格，trim 掉首尾空格后应该算合法。所以校验一律基于 `value.trim()`。

### 第 8 条 · `should_trim_padding`

**它在钉什么**：前台不小心传了首尾空格，应该被**归一化**掉，而不是直接拒绝。

**① 写测试**

```java
@Test
@DisplayName("首尾空格 → 自动去掉")
void should_trim_padding() {
    assertThat(new Username("  zhanghao  ").value()).isEqualTo("zhanghao");
}
```

**② 跑 → 断言红**

现在 `this.value = value` 存的是原始串，`value()` 返回 `"  zhanghao  "`（带空格），不等于 `"zhanghao"` →

```text
[ERROR] UsernameTest.should_trim_padding
[ERROR]   expected: "zhanghao"
[ERROR]    but was: "  zhanghao  "
[INFO] Tests run: 1, Failures: 1
```

**③ 补实现 → 绿**（就改一行）

```java
this.value = value.trim();
```

⚠️ **必须是最后一行**。所有校验都读 `value.trim()`，赋值时再 trim；顺序反了会把"trim 之后才发现是空"这种情况漏掉。

**④ 跑 → 绿**

> 顺便回头想一下第 2 条：`"   "` 为什么被拒？因为它 trim 之后是空串，命中了第 2 条的规则。**所以 trim 必须在校验之前发生**（体现在代码里就是"校验读 trim 值"）。第 2 条和第 8 条合起来才把 trim 这件事说完整 —— 这就是把它们分成两条测试的价值。

### 第 9 条 · `should_be_equal_when_same_value`

**它在钉什么**：两个值相同的 `Username` 必须**彼此相等**，且 `hashCode` 一致。

**① 写测试**

```java
@Test
@DisplayName("同值的 Username 相等，且 hashCode 一致")
void should_be_equal_when_same_value() {
    Username a = new Username("zhanghao");
    Username b = new Username("zhanghao");

    assertThat(a).isEqualTo(b);
    assertThat(a.hashCode()).isEqualTo(b.hashCode());
}
```

**② 跑 → 断言红**

因为 `Username` 没重写 `equals`，用的是 `Object.equals`（比**内存地址**）。`a` 和 `b` 是两个不同对象 → 不相等 →

```text
[ERROR]   expected: "Username@1a2b3c"
[ERROR]    but was:  "Username@4d5e6f"
```

**③ 补实现 → 绿**（重写 `equals` 和 `hashCode`）

```java
@Override
public boolean equals(Object o) {
    if (this == o) {
        return true;
    }
    if (!(o instanceof Username)) {
        return false;
    }
    return Objects.equals(value, ((Username) o).value);
}

@Override
public int hashCode() {
    return Objects.hash(value);
}
```

记得 `import java.util.Objects;`。

**④ 跑 → 绿**

> **为什么两个方法要一起重写**：Java 的契约是「`equals` 相等 → `hashCode` 必须相等」。
> 只重写 `equals` 不重写 `hashCode`，HashMap 就会认为两个"相等"的对象落在**不同的桶**里 —— 存进去取不出来。这正是第 10 条要单独测的东西。
> **`equals` 里那三行的顺序也有讲究**：先比地址（`this == o`，最快，常见场景），再比类型（类型不对直接 false，还能防 `null` —— `null instanceof Username` 就是 `false`），最后才比值。

### 第 10 条 · `should_work_as_map_key`

**它在钉什么**：`Username` 要能当 `HashMap` 的 key。这是第 9 条在**真实场景**下的验收。

**① 写测试**

```java
@Test
@DisplayName("可以作为 HashMap 的 key，用等值的 Username 能取回")

    Map<Username, String> cache = new HashMap<>();
    cache.put(new Username("zhanghao"), "用户缓存");

    assertThat(cache.get(new Username("zhanghao"))).isEqualTo("用户缓存");
}
```

记得 `import java.util.HashMap;` 和 `import java.util.Map;`。

**② 跑 → 直接绿**（第 9 条已经把 `equals` + `hashCode` 都写了）

绿了就下一条。

> **那这条是不是白写了？** 不是。它防的是**只有第 9 条被满足、但用法不对**的情况：如果哪天有人把 `hashCode` 改成 `return 1;`（合法但极差 —— 所有对象挤一个桶），第 9 条照样绿，第 10 条也绿，但性能崩了；如果 `hashCode` 和 `equals` 用**不同的字段**（比如 `hashCode` 用了 `value`，`equals` 用了 `value.length()`），第 10 条就会红，第 9 条反而可能假绿。
> **一条测"契约"，一条测"用途"** —— 这在后面 `User`、`Token` 上会重复出现。

## 4.5 如果你一次写完了实现：补做「手工变异测试」

**先说清楚发生了什么**：把 10 条实现一次性写完（而不是一条条被测试催出来），
代码**不一定错**，但你**失去了"每条测试真的在管那件事"的证据**。
比如只重写了 `equals` 忘了 `hashCode`，第 9 条会红吗？不知道 —— 因为你从来没让它单独红过。

**不用回炉重写。** 用「手工变异测试」补回证据：**故意破坏一行实现，看是否只有对应的测试变红。**

做法：改一行 → 跑 → 记下哪几条红了 → **改回去** → 再跑 → 必须全绿。

### 三个最值的实验（每个约 1 分钟；下表结果是**实测**的，不是推测）

| # | 故意改成 | 实测结果 | 它在证明什么 |
|---|---|---|---|
| 1 | **删掉**字符集判断那段 `if (!value.trim().matches(...))` | **只有第 7 条红** | 第 7 条真的在管字符集，不是被长度规则顺带拦掉的（回想"张三"那个假绿） |
| 2 | 把 `trimmed.length() < MIN_LENGTH` 改成 `<= MIN_LENGTH` | **只有第 5 条红**（第 3 条仍绿） | 第 5 条守的正是"4 是合法的"这一侧。**只测第 3 条锁不住这道门** |
| 3 | **删掉** `hashCode()` 方法 | **第 9 条红 + 第 10 条也红** | 见下 |

第 3 个实验的实测输出值得看一眼：

```text
[FAIL] should_be_equal_when_same_value  expected: 2001112025  but was: 125130493
[FAIL] should_work_as_map_key           expected: "缓存"        but was: null
```

**这就是第 10 条存在的意义**：删掉 `hashCode` 后，`equals` 还是好的（第 9 条前半段照样过），
但 `HashMap` 认为两个"相等"的对象落在**不同的桶**里 → `get()` 返回 `null`。
第 9 条只能证明"两个 hashCode 值不相等"，**第 10 条才能证明"这东西真的能当 key 用"**。
一条测契约，一条测用途 —— 两条都留着。

> **为什么这招值得学**：它是「**变异测试**（mutation testing）」的手工版 ——
> 工业界的自动化变异测试工具（PIT 等）干的就是这件事：自动改你的代码，看测试能不能抓住。
> 抓不住的那一行，说明**你的测试是白写的**。这是判断"测试到底有没有用"的唯一可靠办法。

### 补完之后

1. 每一处改动**务必改回原样**，最后跑一次全量必须全绿；
2. 补上还缺的第 10 条 `should_work_as_map_key`（测试里那 10 条你写了 9 条）；
3. 然后才提交。

## 5. 做完之后 `Username.java` 的完整样子（**先自己写完再看**）

<details>
<summary>点开对照（建议 10 条全绿之后再核对）</summary>

```java
package com.mall.auth.domain.model;

import java.util.Objects;

public final class Username {

    private static final int MIN_LENGTH = 4;
    private static final int MAX_LENGTH = 20;
    private static final String ALLOWED_PATTERN = "^[A-Za-z0-9_]+$";

    private final String value;

    public Username(String value) {
        if (value == null || value.trim().isEmpty()) {
            throw new IllegalArgumentException("用户名不能为空");
        }
        String trimmed = value.trim();
        if (trimmed.length() < MIN_LENGTH) {
            throw new IllegalArgumentException("用户名长度不能少于 " + MIN_LENGTH + " 位");
        }
        if (trimmed.length() > MAX_LENGTH) {
            throw new IllegalArgumentException("用户名长度不能超过 " + MAX_LENGTH + " 位");
        }
        if (!trimmed.matches(ALLOWED_PATTERN)) {
            throw new IllegalArgumentException("用户名只能包含字母、数字和下划线");
        }
        this.value = trimmed;
    }

    public String value() {
        return value;
    }

    @Override
    public boolean equals(Object o) {
        if (this == o) {
            return true;
        }
        if (!(o instanceof Username)) {
            return false;
        }
        return Objects.equals(value, ((Username) o).value);
    }

    @Override
    public int hashCode() {
        return Objects.hash(value);
    }

    @Override
    public String toString() {
        return "Username{" + value + "}";
    }
}
```

**注意最后那个小改动**：真正写的时候你自然会想抽一个局部变量 `String trimmed = value.trim();`，避免 trim 五次。这个动作发生在**第 8 条之后的重构环节**，改完立刻跑全量 → 仍全绿，就可以提交。这就是"重构"的定义：**测试全绿前提下的结构调整，行为一点不变。**

</details>

## 6. 这份搞懂了，B1.2 / B1.3 / B1.4 就是同一套
