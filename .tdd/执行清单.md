### 0.1.1 分支策略：`main` 必须对老师可见 ⚠️

**每完成一个批次，除了在自己分支提交，还要把 `main` 往前推一次。** 否则老师看不到你的新代码。

```bash
cd "/d/demo/commerce platform"
git checkout main
git merge feature/tdd-mall-auth        # 把分支上的提交搬到 main
git push origin main                   # 老师看到的就是这一步
git checkout feature/tdd-mall-auth     # 切回来继续写
```

**更省事的做法（一个人做课程项目推荐）**：**直接在 `main` 上开发**，别切来切去。
反正只有你一个人在写，分分支的"隔离"收益不大，反而多一层"忘了合并"的风险。

| 做法 | 适合 |
|---|---|
| 只在 `main` 上提交 | **一个人做课程项目（推荐）** |
| 分支开发 + 每批次合并回 `main` | 想留"功能分支"这条过程痕迹给老师看 |
| 只在分支上写、从不合并 | ❌ 老师会看不到你的工作 |

> 判断方法：打开 `https://github.com/<你的用户名>/b2c_mall` —— **这个页面显示的就是 `main`**。
> 你在这里看不到的东西，老师也看不到。

## 固定动作：每批次都套这个（简称 SOU）

```text
1. 打开本批次的测试文件（第一次做 = 新建）
2. 只写 1 个测试方法
3. 跑 → 红        （mvn -B -pl mall-auth test -Dtest=XxxTest）
4. 补最小生产代码让它能编译 → 再跑 → 从「编译红」变「断言红」
5. 补实现 → 跑 → 绿
6. 还有用例没写？回到第 2 步，加下一个
7. 本批次用例写完 → 跑全量 → 全绿
8. 重构（可选）→ 再跑 → 仍绿
9. 去 PROGRESS.md 把本批次的任务项打勾
10. git add -A && git commit -m "..."
```

第 3 步那行命令里 `-Dtest=XxxTest` 换成你当前在写的测试类名。跑全量就去掉 `-Dtest`。

**判断红是哪一种**：`Tests run:` 出现了 → 断言红；只有 `BUILD FAILURE` 且报 `找不到符号` → 编译红。

### B1.2 · `RawPassword`（1.2.1 ~ 1.2.4）

> 📖 **本批次有逐条详解**：`B1.2-B1.3-密码值对象-详解.md` 第 3 节。里面讲清了三处**不能照抄 `Username`** 的地方

**新建**：`RawPasswordTest` / `RawPassword`

| # | 方法名 | 断言要点 |
|---|---|---|
| 1 | `should_reject_when_password_is_null` | 抛 `IllegalArgumentException` |

| 3 | `should_reject_when_length_is_5` | 抛异常 |

| 6 | `should_reject_when_length_is_33` | 抛异常 |

**登录视角下 `User` 是"重建"出来的，不是"新建"的** —— 所以用静态工厂 `reconstitute(...)`，

| # | 方法名 | 断言要点 |
|---|---|---|
| 1 | `should_have_only_two_status_values` | `UserStatus.values()` 恰好是 `ENABLED`、`DISABLED` |
| 2 | `should_report_loginable_when_enabled` | `ENABLED.isLoginable()` 为 `true` |
| 3 | `should_not_report_loginable_when_disabled` | `DISABLED.isLoginable()` 为 `false` |
| 4 | ★ `should_treat_null_status_as_not_loginable` | `UserStatus.from(null)` **不是** `ENABLED`（`tb_user.status` 有 `DEFAULT 1`，但历史数据可能真为 `NULL`） |

| 6 | `should_reconstitute_when_optional_fields_absent` | 昵称、头像为 `null` 时也能重建成功 |
| 7 | ◇ `should_be_immutable` | 反射：字段全 `final`、无 setter |

**第 4 条为什么是 ★**：它是**防"默认放开"**的断言。`status == null` 时如果代码写成

### B2.2 · `UserLoggedInEvent`（6.1.1 ~ 6.1.4）

**新建**：`test/.../domain/event/UserLoggedInEventTest.java` / `main/.../domain/event/UserLoggedInEvent.java`

| # | 方法名 | 断言要点 |
|---|---|---|
| 1 | `should_carry_all_payload` | `userId` / `username` / `ip` / `device` / `occurredAt` 逐个断言 |
| 2 | `should_use_injected_clock` | `occurredAt` 来自固定时钟 |
| 3 | ★ `should_not_use_system_clock` | **同一固定时钟连续构造两个事件，`occurredAt` 完全相同** |
| 4 | ◇ `should_be_immutable` | 反射：字段全 `final`、无 setter |

**新建**：`test/.../infrastructure/token/InMemoryTokenStoreTest.java` / `main/.../infrastructure/token/InMemoryTokenStore.java`

| # | 方法名 | 断言要点 |
|---|---|---|
| 1 | `should_find_saved_token` | `save` 后 `find` 能取回，断言 `userId` / `username` |
| 2 | `should_return_empty_for_unknown_token` | `find(new Token("0"×32))` 为 `Optional.empty()` |

| 5 | ◇ `should_be_replaceable_without_touching_application_tests` | 换一个假实现，`LoginApplicationServiceTest` 一行不改仍全绿 |

**第 4 条的写法**（**不要用 `Thread.sleep`**）：

```java
// 用可变的假时钟：一个 AtomicReference<LocalDateTime> 顶替 TimeProvider
private final AtomicReference<LocalDateTime> now = new AtomicReference<>(LocalDateTime.of(2026,1,1,0,0));
TimeProvider clock = now::get;

InMemoryTokenStore store = new InMemoryTokenStore(clock);   // ★ TTL 从构造参数注入
store.save(token, user);
now.set(now.get().plusMinutes(31));                          // 时间旅行
assertThat(store.find(token)).isEmpty();
```

**第 4 条为什么是 ★**：如果用真实 `sleep(30分钟)` 来写这条测试，你整套测试就废了。
这是"注入时间"这条纪律最有说服力的教材 —— 亲身踩一次比看十遍原则管用。

**实现要点**：内部用 `ConcurrentHashMap<Token, Entry>`，`Entry` 里带 `expiresAt`；
`find` 时判断 `now.isAfter(expiresAt)` 就返回空并顺手清理。

**提交**：`feat(mall-auth): 内存令牌存储与 TTL（5.4.1~5.4.5）`

| 6 | `should_return_500_when_password_mismatch` | `$.code` == 500、`$.msg` == `"密码错误"` |
| 7 | ★ `should_not_return_token_on_failure` | 失败响应里 `$.data` 不存在（**防"失败了还返回个空令牌占位"**） |

**实现要点**：`LoginRequest` 上用 `@NotBlank`；`GlobalExceptionHandler` 把
`IllegalArgumentException` / `MethodArgumentNotValidException` 统一转成 `ApiResult(500, msg)`；
**Controller 里不写任何业务判断**，只做 `LoginRequest → LoginCommand` 和 `LoginResult → ApiResult` 两次转换。

**注意**：`LoginResult`（应用层）→ `ApiResult`（web 层）的这个转换就是"协议中立"的回报。
将来要换 gRPC 或加移动端协议，只换 adapter，`LoginApplicationService` 一行不动。

**提交**：`feat(mall-auth): 登录接口与全局异常处理（1.4/2.3/3.4）`

## M6 · 观察者（事件监听器）

### B6.1 · `LoginLogListener`（6.3.1 ~ 6.3.3）

**新建**：`LoginLog` 实体 + `LoginLogRepository` 端口 + `LoginLogListener` + `LoginLogListenerTest`

**这一批不需要 Spring** —— 监听器是普通类，直接 `@Mock` 仓储 + `@InjectMocks` 监听器。

| # | 方法名 | 断言要点 |
|---|---|---|
| 1 | `should_insert_exactly_one_log` | `verify(loginLogRepository, times(1)).insert(any())` |
| 2 | `should_fill_ip_device_and_user_type` | 捕获入参：`ip` / `device` 取自事件，`userType` == `"buyer"`，`status` == 1 |
| 2b | `should_tolerate_null_ip_and_device` | 事件里 ip/device 为 `null` 时也能写入（请求可能没有 `User-Agent`） |
| 3 | ★ `should_not_propagate_exception` | 桩 `insert` 抛异常，`assertThatCode(...).doesNotThrowAnyException()` |

**第 3 条就是实现要点**：

```java
try {
    loginLogRepository.insert(log);
} catch (Exception e) {
    log.warn("登录日志写入失败，不影响登录主流程", e);   // ★ 吞掉，不冒泡
}
```

**原因**：Spring 事件默认**同步**调用。监听器抛出的异常会直接冒泡回 `login()`，
结果是"登录明明成功了，接口却返回 500"。

**提交**：`feat(mall-auth): 登录日志监听器（6.3.1~6.3.3）`

## 卡住时的决策树

| 症状 | 多半是 | 怎么办 |
|---|---|---|
| `找不到符号` | 这是**编译红**，正常 | 建空壳让测试能编译，别急着实现 |
| `Tests run: 0` + `BUILD SUCCESS` | 测试没被 surefire 执行 | 检查 surefire 版本是否还是 3.2.5；`TddWiringSmokeTest` 还在不在 |
| `@Mock` 注入的对象是 `null` | 忘了 `@ExtendWith(MockitoExtension.class)` | 加到测试类上 |
| `UnnecessaryStubbingException` | 桩了但没用到（严格模式） | 把该用例不用的 `when(...)` 删掉 |
| `NoSuchBeanDefinitionException` | `@WebMvcTest` 只加载 web 层 | `LoginApplicationService` 用 `@MockBean` 顶上 |
| `Port 8082 was already in use` | `@SpringBootTest` 起了真容器 | 加 `webEnvironment = WebEnvironment.NONE` |
| `"a".repeat(21)` 编译不过 | Java 8 没有这个 API | 自己写 `repeat()` 工具方法 |
| `List.of()` / `var` 编译不过 | Java 8 语法限制 | 用 `Arrays.asList()` / 显式类型 |
| 断言偶尔红偶尔绿 | 用了真实时间 / 共享状态 | 检查是否偷用了 `LocalDateTime.now()`；用例间不要共享可变状态 |
| 测试跑得越来越慢（秒级） | 有测试偷偷起了 Spring 或连了库 | 看 `target/surefire-reports/*.txt` 里的耗时，把慢的挑出来 |
| `InOrder` 报 `Wanted but not invoked` | 调用顺序和期望不一致 | 这**正是它该报的错** —— 去看实现里的顺序，多半真写反了 |
| 不知道该写什么断言 | 拆解文档里的「测试思路」没翻过来 | 查 `TDD-实操手册.md` 第 4 节的翻译表 |

## 节奏建议

| 阶段 | 一批次大约 | 说明 |
|---|---|---|
| M1 值对象 | 10~20 分钟 | 最快，用来找手感。如果一批超过 40 分钟，说明你在过度设计 |
| M2 聚合根/事件 | 20~30 分钟 | 固定时钟那两条要想清楚 |
| M3 应用编排 | 30~50 分钟 | 最花时间的一层，Mockito 的坑集中在这里 |
| M4 infrastructure | 30~60 分钟 | `@TempDir` + MyBatis 环境搭建一次就好，后面复用 |
| M5 web | 20~30 分钟 | `@WebMvcTest` 的坑不多 |
| M6 观察者 | 20~30 分钟 | 简单 |

**一个判断标准**：如果某个批次你写完了测试、但**一次红都没看见就直接绿了**，
说明你在写"事后测试"，测试没有真正驱动设计 —— 回退，重来。
