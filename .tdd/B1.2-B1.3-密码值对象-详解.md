## 1. 动手前：这一批和 B1.1 的**四条关键差异**

B1.1 是「同一套套路、换一批规则」。但密码这个领域有 4 个地方**必须反着来**，  
照抄 `Username` 一定会踩坑。先花 5 分钟看完这 4 条，再动手。

### 1.1 差异一：`RawPassword` **不做 trim** —— 前后空格是密码的一部分 ⚠️

`Username` 里有一行 `this.value = value.trim();`（第 8 条测试专门钉了它）。

密码**不能**这么干。原因很朴素：

> 用户在注册页输入 `"  abc123  "`，系统偷偷把它变成 `"abc123"` 存下来。  
> 下次登录，同一个用户习惯性地又输入 `"  abc123  "` → 也被 trim → 登录成功。  
> 看起来没问题？**问题在别的客户端**：App 端没做 trim，用户输 `"  abc123  "` → 对不上 → 登录失败。  
> 用户完全不知道为什么「网页能登、App 登不上」。

所以规则是：**密码原样保存，一个字符都不许动。**

|                     | `Username`                   | `RawPassword`                       |
| ------------------- | ---------------------------- | ----------------------------------- |
| 输入 `"  zhanghao  "` | 存成 `"zhanghao"`              | 存成 `"  abc123  "`（原样！）              |
| 实现那行                | `this.value = value.trim();` | `this.value = value;` ← **没有 trim** |
| 判空那行                | `value.trim().isEmpty()`     | `value.isEmpty()` ← **没有 trim**     |

⚠️ **注意判空那行也别改成 `trim().isEmpty()`**。虽然对 `""` 来说两者结果一样，  
但语义上"密码不能是空字符串"和"密码不能是纯空白"是两件事 ——  
`"      "`（6 个空格）**是一个合法的 6 位密码**，只是没人这么用而已。

### 1.2 差异二：密码**没有字符集限制**

`Username` 有正则 `^[A-Za-z0-9_]+$`。密码**不许有**这种限制：

```java
new RawPassword("zh@ng 123!@#")   // ✅ 必须通过，长度 12
```

密码允许任何字符 —— 空格、中文、emoji、`$`、`;` 通通合法。  
**不要去抄 `Username` 的 `ALLOWED_PATTERN`**。

（安全上这叫"不设密码复杂度规则"或"只设长度下限"。真要限制也是限**最短长度**和**最大长度**，  
绝不是限**字符种类**——限字符种类反而会逼用户写 `Password1!` 这种可猜的东西。）

### 1.3 差异三：`RawPassword` **不写** `equals`/`hashCode`，`PasswordHash` **要写**

这是本批次最容易被抄错的一处。B1.1 的 `Username` 有 `equals`/`hashCode`，密码这边要分开看：

|                | 要不要 `equals` / `hashCode` | 为什么                                                                                                                       |
| -------------- | ------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `RawPassword`  | **不要**                    | 它是**瞬时对象**：登录请求进来时创建，比对完立刻丢掉。永远没人拿"这个明文"和"那个明文"比相等，也不会拿它当 `Map` 的 key。写了反而诱导别人写 `if (pw1.equals(pw2))`、把明文对象打进日志 —— 都是坏味道 |
| `PasswordHash` | **要**                     | 它是**长期对象**：要跟着 `User` 落库、进缓存，还要被比较（"这次算出来的哈希和库里那个是不是一样"）。没有值语义，`assertEquals` 会直接失败                                       |

判据很简单，看**任务书有没有要求**：

- B1.2（`RawPassword`）8 条里**没有**"值语义"这条 → 不写
- B1.3（`PasswordHash`）第 5 条就是 `should_be_equal_when_same_hash` → 要写

> 💡 领域设计角度：值对象是否实现 `equals`，取决于它**会不会被当成"值"来比较**。  
> 不是"所有值对象都必须写 `equals`"。

### 1.4 差异四：`toString()` 必须打码 —— 而且这条测试**天生假绿** ⚠️⚠️

这是整份文档里最值钱的一节，请务必看完。

**先说为什么必须打码。**

登录功能比注册功能更容易把密码写进日志，因为出错的路径多：

```java
log.info("登录请求，参数：{}", loginRequest);   // ← loginRequest 里有 RawPassword
log.error("登录失败，用户={}，密码={}", username, password);  // ← 直击要害
```

只要 `RawPassword` 没写 `toString()`，上面两行就会打出 **`RawPassword@4cc77c2e`**（还好）；  
但只要有人图省事写了 `return "RawPassword{" + value + "}";`，  
**明文密码就直接进了日志文件**，而这个日志文件可能被同步到日志平台、被运维看到、被离职员工带走。  
这是真实发生过的一类事故。

所以正确写法是固定返回打码串：

```java
@Override
public String toString() {
    return "RawPassword{***}";
}
```

**再说这一节的坑 —— 这条测试极其容易写成"永远绿"。**

`执行清单.md` 给的断言是：

```java
assertThat(new RawPassword("abc123").toString()).doesNotContain("abc123");
```

看起来很合理。**但它抓不住任何东西。** 实测（`D:\_tmpdoc\b12check`，Java 17 + AssertJ 3.22.0）：

| 实现                                          | `toString()` 实际输出                                 | 只写 `doesNotContain("abc123")` 的结果 |
| ------------------------------------------- | ------------------------------------------------- | --------------------------------- |
| **完全没写 `toString()`**（空壳）                   | `com.mall.auth.domain.model.RawPassword@3930015a` | **`[PASS]`** ← 假的！                |
| 正确打码                                        | `RawPassword{***}`                                | `[PASS]`                          |
| 手贱写成 `return "RawPassword{" + value + "}";` | `RawPassword{abc123}`                             | `[FAIL]` ← 只有这种才抓得到               |

原因很直白：**Java 默认的 `Object.toString()` 本来就只输出"类名@哈希码"，不含任何字段值。**  
你不写打码，它**天然**就"不含明文"。所以这条断言在空壳下就能过 —— 它测的是"恰好为真的偶然事实"，  
不是"我实现了打码"。

**修法：加一条"锚点断言"。** 实测对比：

| 测试写法                                                             | 实现=没有 `toString()` | 实现=正确打码  |
| ---------------------------------------------------------------- | ------------------ | -------- |
| 只写 `doesNotContain("abc123")`                                    | ❌ `[PASS]`（假绿）     | `[PASS]` |
| `doesNotContain("abc123")` **+** `isEqualTo("RawPassword{***}")` | ✅ `[FAIL]`         | `[PASS]` |

所以正确写法是**两条断言**：

```java
@Test
void should_not_leak_plaintext_in_toString() {
    String text = new RawPassword("abc123").toString();

    assertThat(text).doesNotContain("abc123");              // ① 意图：不泄漏明文
    assertThat(text).isEqualTo("RawPassword{***}");         // ② 锚点：确实覆写了，且打码了
}
```

**② 为什么必须有？** 因为 ① 单独存在时，默认 `Object.toString()` 就能满足它。  
② 把"必须覆写 `toString()`"这件事**钉死**了 —— 默认输出是 `com...RawPassword@3930015a`，  
永远不可能等于 `"RawPassword{***}"`。

> 💡 **可以推广的一条规则**：  
> 凡是"断言某个东西**不包含**某个值"的测试，都要问自己一句：  
> **"那我不做任何事的时候，它包含吗？"** 如果不包含，这条测试就是白写的。  
> 通用做法：**加一条正向锚点**，把"我确实做了这件事"也钉住。

同样的坑在 B1.3 的 `should_mask_value_in_toString` 里**一模一样**（实测同样是假绿），  
那边我不再重复讲原理，你按同样的两条断言写。

## 2. 一份实测：这一批哪些用例"天生就是绿的"

为了避免你在红绿循环里困惑"怎么这条一写就是绿的"，我把这一批全部 16 条用例  
在一份**空壳实现**（只有 `private final String value` + 无校验构造 + `value()` 取值方法）上跑了一遍。

结果：**PASS = 6 / 16，FAIL = 10。**

**空壳下就绿的那 6 条（= 不会驱动你写任何代码）：**

| 用例                                                        | 类别           | 为什么天生绿                         |
| --------------------------------------------------------- | ------------ | ------------------------------ |
| `RawPasswordTest.should_accept_when_length_is_6`          | **接受型**      | 空壳不校验长度，`"abc123"` 当然通过        |
| `RawPasswordTest.should_accept_when_length_is_32`         | **接受型**      | 同上                             |
| `RawPasswordTest.should_preserve_spaces_without_trimming` | **接受型 + 护栏** | 空壳不 trim，天然保留空格（它的价值见 §5 EXP4） |
| `RawPasswordTest.should_have_no_setter`                   | **◇ 护栏型**    | 空壳本来就没有 setter                 |
| `PasswordHashTest.should_not_expose_plaintext_accessor`   | **◇ 护栏型**    | 空壳本来就没有 `plain()`              |
| `PasswordHashTest.should_keep_value_intact`               | **接受型**      | 空壳原样存取                         |

**空壳下会红的 10 条（= 真正驱动你写实现的）：**

`should_reject_when_password_is_null` / `_empty` / `_length_is_5` / `_length_is_33` /  
`should_not_leak_plaintext_in_toString` / `should_reject_when_hash_is_null` / `_blank` /  
`should_mask_value_in_toString` / `should_be_equal_when_same_hash` / `should_reject_when_hash_is_not_bcrypt`

**这张表要你记住两件事：**

1. **"接受型"和"护栏型"测试天生就是绿的，这不是 bug。**  
   它们不负责把事情从红变绿，它们负责**上锁**：锁住"6 位也算合法"、锁住"不许有 setter"。  
   将来有人把 `MIN_LENGTH` 改成 7，或者（更可能的）有人图方便加了 setter，这些锁就会响。
2. **反过来，如果一条"拒绝型"测试一写出来就是绿的，那就有问题了** —— 要么是你实现已经写好了，  
   要么是**测试数据本身就不合法**（B1.1 那个 `"张三"` 假绿坑就是这类）。

### 第 1 条 · `should_reject_when_password_is_null`

**先写测试**：

```java
import static org.assertj.core.api.Assertions.assertThatThrownBy;

@Test
void should_reject_when_password_is_null() {
    assertThatThrownBy(() -> new RawPassword(null))
            .isInstanceOf(IllegalArgumentException.class);
}
```

**跑一下，你会看到（第一次是编译红）**：

```
找不到符号
  符号: 类 RawPassword
```

这是**编译红** —— 注意屏幕上**没有 `Tests run:`**。`RawPassword` 类还不存在，测试代码根本编译不过。

> ⚠️ 记住这个区分：**没有 `Tests run:` = 编译红；有 `Tests run: N` = 真的在跑测试。**  
> 详见 `B1.1-Username-详解.md` §7 第 1 行。

**现在建 `RawPassword` 空壳。**

`mall-auth/src/main/java/com/mall/auth/domain/model/` 右键 → New → Java Class → `RawPassword`，写成：

```java
package com.mall.auth.domain.model;

public final class RawPassword {

    private final String value;

    public RawPassword(String value) {
        this.value = value;
    }

    public String value() {
        return value;
    }
}
```

再跑一次，这次的输出变成**断言红**：

```
Tests run: 1, Failures: 1, Errors: 0, Skipped: 0
java.lang.AssertionError
Expecting code to raise a throwable.
```

`Expecting code to raise a throwable` = 「我期望这段代码抛异常，它却安安稳稳地跑完了」。  
正是我们想要的：空壳构造方法不校验，`null` 也照收。

**现在写实现 —— 最少只写这一句：**

```java
public RawPassword(String value) {
    if (value == null) {
        throw new IllegalArgumentException("密码不能为空");
    }
    this.value = value;
}
```

再跑 → 绿。

> 💡 **为什么这里只判 `null`，不顺手把 `isEmpty()` 一起写了？**  
> 因为第 2 条测试就是来钉"空串"的。**一次只让一条用例从红变绿**，这是整份手册里最核心的纪律。  
> 你现在多写一行，第 2 条就永远看不到红，也就永远不知道它到底在测什么。

⚠️ 判据是 **`IllegalArgumentException`，不是 `NullPointerException`** —— 理由和 B1.1 第 1 条完全一样  
（"主动拒绝"vs"没料到崩了"），不重复讲了，翻 `B1.1-Username-详解.md` §1.2。

### 第 2 条 · `should_reject_when_password_is_empty`

**先写测试**：

```java
@Test
void should_reject_when_password_is_empty() {
    assertThatThrownBy(() -> new RawPassword(""))
            .isInstanceOf(IllegalArgumentException.class)
            .hasMessageContaining("密码");
}
```

跑 → 红（`Expecting code to raise a throwable`，因为 `""` 现在能通过）。

**现在改实现**：

```java
public RawPassword(String value) {
    if (value == null || value.isEmpty()) {      // ← 把条件「扩成」这样
        throw new IllegalArgumentException("密码不能为空");
    }
    this.value = value;
}
```

⚠️⚠️ **这里就是 B1.1 那个"冗余 if"坑的高发点。**

正确动作是**改那一行 if 的条件**（把 `value == null` 扩写成 `value == null || value.isEmpty()`），  
**不是**在下面再加一个 `if (value.isEmpty())`。

如果你加了第二个 if，IDEA 会给你黄色波浪线：

```
Condition 'value == null' is always 'false'
```

意思是：第一个 if 已经把 `null` 抛掉了，第二个 if 里的 `value == null` 永远为假 —— 死条件。  
测试照样绿，但代码是绕的。看到这条黄线，**该做的动作是"重构"**：把重复的判断删掉，合并成一个条件。

**再看一眼这里为什么用 `isEmpty()` 而不是 `trim().isEmpty()`** —— 回到 §1.1：  
密码里的空格有意义，`"      "` 是合法的 6 位密码。这是有意为之，不是漏写。

> 📌 诚实地说：**这一批里没有任何一条测试能抓住"你写成了 `trim().isEmpty()`"**。  
> 如果你想把这条规则也钉死，可以加一条可选用例（见本节末尾）。知道自己的测试边界在哪，比测试多两条更重要。

### 第 3 条 · `should_reject_when_length_is_5`

**先写测试**：

```java
@Test
void should_reject_when_length_is_5() {
    assertThatThrownBy(() -> new RawPassword("abc12"))     // 数一下：a b c 1 2 = 5 位
            .isInstanceOf(IllegalArgumentException.class);
}
```

跑 → 红。

**现在写实现**：加常量 + 下界判断。

```java
private static final int MIN_LENGTH = 6;

public RawPassword(String value) {
    if (value == null || value.isEmpty()) {
        throw new IllegalArgumentException("密码不能为空");
    }
    if (value.length() < MIN_LENGTH) {
        throw new IllegalArgumentException("密码长度不能少于 " + MIN_LENGTH + " 位");
    }
    this.value = value;
}
```


跑 → 绿。

> 💡 `"abc12"` 只有 5 位，所以会被新加的下界判断拦住 —— 测试数据必须**只违反一条规则**，  
> 否则你分不清是哪个 if 拦住的它（B1.1 的"假绿"教训）。

### 第 4 条 · `should_accept_when_length_is_6`

**先写测试**：

```java
@Test
void should_accept_when_length_is_6() {
    assertThat(new RawPassword("abc123").value()).isEqualTo("abc123");
}
```

**跑一下 —— 这次它会直接绿。**

不要怀疑自己写错了。这是 §2 表里说的**接受型测试**：  
它测的是"6 位是合法的"，而你的实现此刻只有下界判断 `length() < 6`，  
`"abc123"` 长度正好 6 → 不满足 `< 6` → 通过。

**它的价值不是"催你写代码"，是"上锁"**：  
如果哪天有人把 `MIN_LENGTH` 改成 `7`，或者把 `<` 手滑写成 `<=`，这条就会立刻变红。

> 💡 **但注意一个更微妙的作用** —— 它是**闭区间**的证明。  
> 只测 `should_reject_when_length_is_5`，你无法区分实现是 `length() < 6`（正确）还是 `length() <= 5`（也正确）  
> ……这两个本来就是等价的。  
> 真正的价值在于：它和"第 3 条"配对，把边界从**两侧**夹住了 —— 5 位必须拒，6 位必须收。  
> **这才是完整的边界测试：拒绝侧 + 接受侧都要有。**

```java
@Test
void should_accept_when_length_is_32() {
```

### 第 6 条 · `should_reject_when_length_is_33`

**先写测试**：

```java
@Test
void should_reject_when_length_is_33() {
    assertThatThrownBy(() -> new RawPassword(P33))
            .isInstanceOf(IllegalArgumentException.class);
}
```

跑 → **红**（这条不是接受型，`P33` 现在能通过）。

**现在写实现**：

```java
private static final int MAX_LENGTH = 32;
```

### 第 8 条 · ◇ `should_have_no_setter`（反射护栏）

**先写测试** —— 这条要 `import` 两个反射相关的东西：

```java
            .extracting(Method::getName)

```

跑 → **绿**（空壳本来就没有 setter，见 §2）。

- **第一段**：类里不许出现任何 `setXxx` 方法
- **第二段**：所有字段必须是 `final`（`private static final int MIN_LENGTH` 也满足）

| 代码                                           | 意思                                                          |
| -------------------------------------------- | ----------------------------------------------------------- |

| `.noneMatch(name -> name.startsWith("set"))` | 断言"一个都不以 `set` 开头"                                          |
| `Modifier.isFinal(f.getModifiers())`         | 判断字段有没有 `final` 修饰符（`Modifier` 是 `java.lang.reflect` 里的工具类） |

> ⚠️ 常见报错：少了 `import java.lang.reflect.Modifier;` → `找不到符号: 类 Modifier`。

> 💬 **为什么标 ◇？** ◇ 是"可选/可跳过"的意思（见 `执行清单.md` 的图例）。

## 4. B1.3 · `PasswordHash` 五条逐个展开

**先说清楚这个类是什么。** `PasswordHash` 装的**不是密码**，是 `BCryptPasswordEncoder`  
算出来的那串哈希，长这样：

```
$2a$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy
```

它要能从数据库读出来、能塞回数据库，但**永远不能变回明文**（BCrypt 是单向的，这本来也做不到）。

所以它的职责只有两件：

1. **标明身份** —— 这是个"哈希"，别把它当别的东西用
2. **不添乱** —— 打印、比较的时候别出洋相

> ⚠️ 有一个反直觉的点先说在前面：**`PasswordHash` 必须保留 `value()` 方法**。  
> 因为仓储层要靠它把哈希写进数据库。所以"防泄漏"靠的不是"藏起来"，  
> 而是"**不提供任何返回明文的途径**"（◇ 第 3 条）+ "打印时打码"（★ 第 4 条）。

**测试类骨架**：同 B1.2，先建 `PasswordHashTest` 空类，加一个 BCrypt 样例常量：

```java
public class PasswordHashTest {

    private static final String BCRYPT =
            "$2a$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy";
}
```

> 💡 这串是 BCrypt 的经典测试样例，**总长 60 位**（实测确认）。  
> 你也可以换成自己用 `BCryptPasswordEncoder` 生成的任意一条。用现成的更省事。

### 可选加分：校验 BCrypt 格式（第 6、7 条）

但如果你想让 `PasswordHash` 更"值对象"一点，可以加一条**格式校验**：

**第 6 条**：


```java
@Test

    assertThat(new PasswordHash(BCRYPT).value()).isEqualTo(BCRYPT);
}
```

**实现**（加在空值判断之后）：

```java
import java.util.regex.Pattern;

private static final Pattern BCRYPT_PATTERN =
        Pattern.compile("^\\$2[aby]?\\$\\d{2}\\$[./A-Za-z0-9]{53}$");

// 构造方法里追加：
if (!BCRYPT_PATTERN.matcher(value).matches()) {
    throw new IllegalArgumentException("不是合法的 BCrypt 哈希");
}
```

**这个正则逐段读**（Java 字符串里 `$` 要写成 `\\$`）：

| 片段                  | 匹配                               | 说明                        |
| ------------------- | -------------------------------- | ------------------------- |
| `^\\$2[aby]?\\$`    | `$2a$` / `$2b$` / `$2y$` / `$2$` | BCrypt 的版本前缀              |
| `\\d{2}\\$`         | `10$`                            | **cost 因子**，2 位数（4~31）    |
| `[./A-Za-z0-9]{53}` | 53 个字符                           | Base64 变体字符集（含 `.` 和 `/`） |
| `$`                 | —                                | 结束                        |

**实测核对过**：样例 `$2a$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy` 总长 **60**，  
前缀 `$2a$10$` 占 7 位，60 − 7 = **53**，与 `{53}` 吻合。

**加不加？权衡表：**

|       | 加（7 条）                                    | 不加（5 条，主线）                               |
| ----- | ----------------------------------------- | ---------------------------------------- |
| 好处    | 值对象守护自己的不变量；明文误传进来会被当场拦下                  | 符合任务书；测试更简单；换算法（argon2）不用改代码             |
| 代价    | 超出任务书；测试数据必须是真哈希；硬编码 `{53}` 绑死了 BCrypt 长度 |                                          |
| 什么时候值 | 你希望 `PasswordHash` 承担"我保证我是哈希"的职责         | 校验责任放在上游（`BCryptPasswordEncoderAdapter`） |

> 💡 **我的建议**：**先按 5 条主线做完 + 提交**，然后再加这两条，作为**第二次提交**：  
> `feat(mall-auth): PasswordHash 增加 BCrypt 格式校验`  
> 这样你的 TDD 历史里会多出一个漂亮的"增量"痕迹 —— 老师看到的是"**他做完之后又主动加严了约束**"，

## 5. 手工变异测试（6 个实验，全部实测）

**什么时候做这个**：如果你像我一样，"一条一条跑红绿"这个节奏没走完整  
（比如一次就把 `RawPassword` 写完了），用这个办法**补回证据**。

**方法**：故意把实现破坏一行，跑一次测试，**看是不是只有对应的那条变红**。  
如果红了一片 —— 说明测试之间互相耦合；如果一条都不红 —— 说明**这个缺陷根本没有测试能发现**。

下面 6 个实验是我在 Java 17 + AssertJ 3.22.0 上**真跑出来的结果**，不是推测：

| 实验       | 把实现改成                                                | 结果             | 挂的用例                                      |
| -------- | ---------------------------------------------------- | -------------- | ----------------------------------------- |
| **EXP1** | `toString()` 返回 `"RawPassword{" + value + "}"`（打码失效） | `PASS = 15/16` | `should_not_leak_plaintext_in_toString`   |
| **EXP2** | `MIN_LENGTH = 6` → `5`                               | `PASS = 15/16` | `should_reject_when_length_is_5`          |
| **EXP3** | `MAX_LENGTH = 32` → `33`                             | `PASS = 15/16` | `should_reject_when_length_is_33`         |
| **EXP4** | 构造里 `this.value = value` → `value.trim()`            | `PASS = 15/16` | `should_preserve_spaces_without_trimming` |
| **EXP5** | `equals` 里 `Objects.equals(...)` → `this == o`       | `PASS = 15/16` | `should_be_equal_when_same_hash`          |
| **EXP6** | `PasswordHash.toString()` 改成输出真实哈希                   | `PASS = 15/16` | `should_mask_value_in_toString`           |

**6 个实验，每个都恰好挂 1 条，且挂的正是对应的那条。**

这说明什么？**你的测试是"精确"的** —— 每条测试负责一个实现细节，互不打架。  
这比"测试很多但都是糊在一起"强得多。

### 最有价值的是 EXP4

因为它是**最反直觉**的一个：

> 破坏方式：在构造里加一个 `.trim()`。  
> 这在 `Username` 里是**正确的**（B1.1 第 8 条要求它 trim），  
> 在 `RawPassword` 里是**错误的**。而在 `RawPassword` 里，**只有一条**测试能发现它  
> —— 就是那条"清单表里原本没有、我建议你补上"的 `should_preserve_spaces_without_trimming`。

**这就是"补一条测试"的实际价值**：没有它，你照着 `Username` 抄个 trim 进来，

```java
package com.mall.auth.domain.model;

public final class RawPassword {

    private static final int MIN_LENGTH = 6;
    private static final int MAX_LENGTH = 32;

    private final String value;

    public RawPassword(String value) {
        if (value == null || value.isEmpty()) {
            throw new IllegalArgumentException("密码不能为空");
        }
        if (value.length() < MIN_LENGTH) {
            throw new IllegalArgumentException("密码长度不能少于 " + MIN_LENGTH + " 位");
        }
        if (value.length() > MAX_LENGTH) {
            throw new IllegalArgumentException("密码长度不能超过 " + MAX_LENGTH + " 位");
        }
        this.value = value;              // 不 trim，空格是密码的一部分
    }

    public String value() {
        return value;
    }

    @Override
    public String toString() {
        return "RawPassword{***}";
    }
    // 注意：没有 equals / hashCode —— 瞬时对象不需要
}
```

```java
package com.mall.auth.domain.model;

import java.util.Objects;

public final class PasswordHash {

    private final String value;

    public PasswordHash(String value) {
        if (value == null || value.trim().isEmpty()) {
            throw new IllegalArgumentException("密码哈希不能为空");
        }
        this.value = value;
    }

    public String value() {
        return value;
    }

    @Override
    public boolean equals(Object o) {
        if (this == o) {
            return true;
        }
        if (!(o instanceof PasswordHash)) {
            return false;
        }
        return Objects.equals(value, ((PasswordHash) o).value);
    }

    @Override
    public int hashCode() {
        return Objects.hash(value);
    }

    @Override
    public String toString() {
        return "PasswordHash{***}";
    }
}
```
