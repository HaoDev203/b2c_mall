## 需求概述

在 b2c 商城的 `mall-auth` 服务中实现前台买家的「用户名 + 密码」**注册**。用户提交用户名、密码（昵称与手机号可选），系统校验输入合法性与用户名唯一性，将密码以 BCrypt 哈希落库，初始化账号默认属性，并在注册成功后通过领域事件触发欢迎站内信与审计日志等副作用。**任何失败路径都不得落库、不得发布事件。注册成功只返回结果标识，不签发 token。**

### 输入需求（原文）

```text
在 b2c 商城的 mall-auth 服务中实现「用户名 + 密码」注册，具体包括：
1. 用户通过 HTTP 接口提交用户名、密码，以及可选的昵称、手机号；
2. 用户名/密码为空、或格式非法（长度、字符集）时，直接拒绝并给出明确提示；
3. 用户名必须全局唯一，重复注册要拒绝；
4. 密码不得明文落库，必须以 BCrypt 哈希存储；
5. 注册成功后返回成功标识，并初始化账号（默认头像、默认昵称、登录次数 0、状态启用）；
6. 注册成功需要发欢迎站内信、写审计日志（副作用，用观察者/事件解耦）；
7. 任何失败路径都不得落库、不得发事件。
如有不清晰的内容使用交互式问答让我解释。
```

### 输入架构（原文）

```text
Spring Cloud Alibaba 微服务项目 b2c_mall 中的独立模块 mall-auth
（Spring Boot 2.7.18 / Java 8，端口 8082）。模块内采用四层结构：

- adapter/web    ：RegisterController + RegisterRequest DTO，只做协议转换，不含业务判断
- application    ：RegisterApplicationService 编排用例（事务、发布事件、调用出站端口）

- infrastructure ：实现 domain / application 定义的出站端口（MyBatis UserRepository、
                   BCryptPasswordEncoderAdapter）

依赖方向：adapter、infrastructure → application → domain。
密码以 BCrypt 哈希存储。
```

## 功能点 1：合法信息可以完成注册（主成功路径）

- **功能上下文 1.1**：domain 层 - 值对象 `Username`（用户名的合法性由类型本身保证，一旦构造成功即合法）
  - **任务项 1.1.1**：`Username` 拒绝 `null`、空串、纯空白串
    - *测试思路*：`assertThatThrownBy(() -> new Username("  ")).isInstanceOf(IllegalArgumentException.class).hasMessageContaining("用户名")`；`null` 与 `""` 各写一个用例，验证抛出的都是 `IllegalArgumentException` 而不是 `NullPointerException`
  - **任务项 1.1.2**：`Username` 长度边界为 4~20（含两端）
    - *测试思路*：**边界四连测** —— 3 位抛异常、4 位通过、20 位通过、21 位抛异常。这是"验证 Fail/Pass 边界"的典型：两侧各越界一格，中间各取一位
  - **任务项 1.1.3**：`Username` 只接受字母、数字、下划线
    - *测试思路*：`"zhang hao"`（空格）、`"张三"`（中文）、`"zh@ng"`（符号）三种各断言抛 `IllegalArgumentException`
  - **任务项 1.1.4**：`Username` 构造时自动 trim 前后空白
    - *测试思路*：`assertThat(new Username("  zhanghao  ").value()).isEqualTo("zhanghao")` —— 断言的是"规范化后的值"，而不是"原样保留"
  - **任务项 1.1.5**：`Username` 具备值语义
    - *测试思路*：同值两个对象 `isEqualTo` 为真、`hashCode` 相等；并断言 `new HashMap<>()` 里以 `Username` 为 key 能命中（**只覆写 equals 不覆写 hashCode 会在这里红**）
- **功能上下文 1.2**：domain 层 - 值对象 `RawPassword`（明文密码，生命周期极短）
  - **任务项 1.2.1**：`RawPassword` 拒绝 `null` 与空串
    - *测试思路*：两种输入各断言抛 `IllegalArgumentException`
  - **任务项 1.2.2**：`RawPassword` 长度边界为 6~32
    - *测试思路*：5 位抛异常、6 位通过、32 位通过、33 位抛异常
  - **任务项 1.2.3**：`RawPassword` 无任何可以修改内部状态的方法
    - *测试思路*：用反射断言类中不存在 `setXxx` 开头的公开方法，且字段均为 `final`
  - **任务项 1.2.4**：`RawPassword` 的 `toString()` **不得泄露明文**
    - *测试思路*：`assertThat(new RawPassword("abc123").toString()).doesNotContain("abc123")` —— 这条是安全断言，防止密码被打进日志
- **功能上下文 1.3**：application 层 - `RegisterApplicationService` 主成功路径
  - **任务项 1.3.1**：用户名未被占用时，`UserRepository.save` 被调用且**恰好一次**
    - *测试思路*：`verify(userRepository, times(1)).save(any(User.class))`
  - **任务项 1.3.2**：返回结果是"注册成功"标识，且**不包含 token**
    - *测试思路*：`assertThat(result.getCode()).isEqualTo(200)`；`assertThat(result.getData()).doesNotContain("token")`
  - **任务项 1.3.3**：落库的 `User` 中 username 是 trim 规范化之后的值
    - *测试思路*：用 `ArgumentCaptor<User>` 捕获入参，断言 `captor.getValue().username().value()).isEqualTo("zhanghao")`（传入 `" zhanghao "` 时）
- **功能上下文 1.4**：adapter/web 层 - `RegisterController`
  - **任务项 1.4.1**：`POST /auth/register` 接收 JSON 并返回 HTTP 200 + 业务码 200
    - *测试思路*：`mockMvc.perform(post("/auth/register").contentType(APPLICATION_JSON).content(json)).andExpect(status().isOk()).andExpect(jsonPath("$.code").value(200))`
  - **任务项 1.4.2**：请求体 JSON 中的字段能正确映射到 `RegisterRequest`（含可选的 nickname、phone）
    - *测试思路*：只传 username+password 时也返回 200（可选字段不该导致失败）
  - **任务项 1.4.3**：进入 Controller 的数据**不做业务判断**，直接交给 Service
    - *测试思路*：用 `@MockBean` 替换 Service 并设置其返回"失败"，断言 Controller 原样返回该失败结果（证明 Controller 没有自作主张）

## 功能点 2：非法输入不让注册

- **功能上下文 2.1**：domain 层 - 校验的归属（规则下沉到值对象，而非散落在 Service）
  - **任务项 2.1.1**：所有输入校验在值对象构造时完成，非法输入**根本构造不出对象**
    - *测试思路*：断言 `new Username("")` 抛异常的同时，也断言 Service 层不存在 `if (StringUtils.isEmpty(...))` 这类分支 —— 用代码评审或 ArchUnit 检查（**可选，需额外引入 `archunit-junit5`**）
  - **任务项 2.1.2**：`Nickname` 允许为空，为空时回落到"用户" + 用户名
    - *测试思路*：`assertThat(Nickname.of(null, new Username("zhanghao")).value()).isEqualTo("用户zhanghao")`；再断言非空时原样保留 `Nickname.of("浩哥", ...).value()` 为 `"浩哥"`
  - **任务项 2.1.3**：`Nickname` 长度上限 20，超长抛异常
    - *测试思路*：20 位通过、21 位抛 `IllegalArgumentException`
  - **任务项 2.1.4**：`Phone` 可为空；非空时必须是 11 位数字
    - *测试思路*：`null` 通过、`""` 通过、`"13800138000"` 通过、`"1380013800"`（10 位）与 `"1380013800a"` 抛异常
- **功能上下文 2.2**：application 层 - 入参守卫与副作用隔离
  - **任务项 2.2.1**：`command` 为 `null` 时立即抛异常，**不得触碰仓储**
    - *测试思路*：`assertThatThrownBy(() -> service.register(null)).isInstanceOf(IllegalArgumentException.class)`，并 `verify(userRepository, never()).save(any())`
  - **任务项 2.2.2**：任何校验失败路径都**不得发布事件**
    - *测试思路*：构造一个会失败的用例，`verify(publisher, never()).publishEvent(any())`
  - **任务项 2.2.3**：校验失败时**不得调用** `PasswordEncoder.encode`（省掉昂贵的 BCrypt 运算）
    - *测试思路*：`verify(passwordEncoder, never()).encode(any())`
- **功能上下文 2.3**：adapter/web 层 - 参数校验与统一错误响应
  - **任务项 2.3.1**：`RegisterRequest` 上用 Bean Validation 注解声明必填约束
    - *测试思路*：缺 username 的 JSON 请求返回非 200 业务码，且 `msg` 中含"用户名"
  - **任务项 2.3.2**：`GlobalExceptionHandler` 把 `IllegalArgumentException` 转成统一 `ApiResult(code=500)`
    - *测试思路*：`mockMvc` 请求非法参数，断言 `$.code` 为 500 且 `$.msg` 非空、**不含 Java 堆栈关键字**（如不出现 `java.lang`）

## 功能点 3：用户名已被占用不让注册

- **功能上下文 3.1**：domain 层 - 出站端口 `UserRepository` 的接口语义
  - **任务项 3.1.1**：`UserRepository` 是接口，且 `domain.port` 包内**零框架依赖**
    - *测试思路*：`grep -r "^import org.springframework" mall-auth/src/main/java/com/mall/auth/domain` 结果为空；端口方法签名只出现领域类型（**可选自动化：ArchUnit**）
  - **任务项 3.1.2**：查重方法签名接受 `Username` 值对象而不是 `String`
    - *测试思路*：`assertThat(UserRepository.class.getMethod("existsByUsername", Username.class)).isNotNull()`，并断言不存在接受 `String` 的重载（编译期类型安全）
- **功能上下文 3.2**：application 层 - 查重分支
  - **任务项 3.2.1**：`existsByUsername` 返回 `true` 时返回"账号已存在"
    - *测试思路*：`when(userRepository.existsByUsername(any())).thenReturn(true)`，断言 `result.getMsg()).isEqualTo("账号已存在")`
  - **任务项 3.2.2**：查重命中时**不得调用** `save` 与 `encode`
    - *测试思路*：`verify(userRepository, never()).save(any())`；`verify(passwordEncoder, never()).encode(any())`
  - **任务项 3.2.3**：`existsByUsername` 返回 `false` 时继续执行保存
    - *测试思路*：`verify(userRepository, times(1)).save(any())`
  - **任务项 3.2.4**：查重必须发生在加密**之前**（顺序断言）
    - *测试思路*：`InOrder inOrder = inOrder(userRepository, passwordEncoder); inOrder.verify(userRepository).existsByUsername(any()); inOrder.verify(passwordEncoder).encode(any());` —— 这条保证"重复用户名不会白白做一次 BCrypt"
- **功能上下文 3.3**：infrastructure 层 - 唯一性兜底（应用层查重有并发窗口，数据库才是最终防线）
  - **任务项 3.3.1**：`tb_user.username` 上有 UNIQUE 约束，重复插入抛异常
    - *测试思路*：内嵌 SQLite 建表后连续插两条同名记录，断言第二次抛 `SQLException`（**真实执行 JDBC，不用 mock**）
  - **任务项 3.3.2**：`MyBatisUserRepository` 把唯一约束冲突翻译成业务异常
    - *测试思路*：断言重复 `save` 抛 `RegistrationRejectedException` 且提示含"账号已存在"，而**不是**把 `SQLException` 直接冒泡给 Controller
- **功能上下文 3.4**：adapter/web 层 - 重复注册的响应
  - **任务项 3.4.1**：重复注册返回业务码 500 + `msg` 为"账号已存在"
    - *测试思路*：`andExpect(jsonPath("$.code").value(500)).andExpect(jsonPath("$.msg").value("账号已存在"))`

## 功能点 4：密码不以明文落库

- **功能上下文 4.1**：domain 层 - 值对象 `PasswordHash`
  - **任务项 4.1.1**：`PasswordHash` 拒绝 `null` 与空串
    - *测试思路*：两种输入各断言抛 `IllegalArgumentException`
  - **任务项 4.1.2**：`PasswordHash` **不提供任何返回明文的途径**
    - *测试思路*：用反射断言该类只有 `value()`（返回哈希）而无 `raw()` / `plain()` 之类方法（**防倒退设计**）
  - **任务项 4.1.3**：`PasswordHash.toString()` 打码
    - *测试思路*：`assertThat(hash.toString()).doesNotContain(hash.value())`，且长度固定输出形如 `PasswordHash{***}`
  - **任务项 4.1.4**：`PasswordHash` 具备值语义
    - *测试思路*：同哈希值两对象 `isEqualTo` 为真
- **功能上下文 4.2**：domain 层 - 出站端口 `PasswordEncoder`
  - **任务项 4.2.1**：端口只声明 `encode(RawPassword) -> PasswordHash`
    - *测试思路*：反射断言该接口只有 1 个方法（**刻意不提供 decode**）
  - **任务项 4.2.2**：端口签名是领域类型进出，不出现 `String`
    - *测试思路*：同 3.1.2 的方式断言方法参数与返回类型
- **功能上下文 4.3**：application 层 - 落库前的加密动作
  - **任务项 4.3.1**：`save` 收到的 `User` 其 `passwordHash` **不等于**明文
    - *测试思路*：`ArgumentCaptor<User>` 捕获后 `assertThat(captor.getValue().passwordHash().value()).isNotEqualTo("abc123")`
  - **任务项 4.3.2**：落库的哈希**就是** `PasswordEncoder.encode` 的返回值
    - *测试思路*：stub `when(passwordEncoder.encode(any())).thenReturn(new PasswordHash("$2a$HASHED"))`，捕获后断言等于 `"$2a$HASHED"`（切断"自己拼字符串假装加密"的可能性）
  - **任务项 4.3.3**：`encode` 恰好被调用一次（不重复加密）
    - *测试思路*：`verify(passwordEncoder, times(1)).encode(any())`
- **功能上下文 4.4**：infrastructure 层 - BCrypt 适配器
  - **任务项 4.4.1**：同一明文两次 `encode` 结果**不同**（验证加盐）
    - *测试思路*：`assertThat(a.value()).isNotEqualTo(b.value())` —— 真实调用 BCrypt，不使用 mock
  - **任务项 4.4.2**：`matches(明文, 哈希)` 为 `true`
    - *测试思路*：`assertThat(encoder.matches(new RawPassword("abc123"), new PasswordHash(hash.value()))).isTrue()`
  - **任务项 4.4.3**：`matches(错误明文, 哈希)` 为 `false`
    - *测试思路*：断言为 `false`（**注意不是抛异常**）
  - **任务项 4.4.4**：哈希长度符合 BCrypt 格式（60 字符、`$2a$` 开头）
    - *测试思路*：`assertThat(hash.value()).hasSize(60).startsWith("$2a$")` —— 防止误把 MD5/明文当哈希

## 功能点 6：注册成功触发副作用（观察者 / 事件解耦）

- **功能上下文 6.1**：domain 层 - 领域事件定义
  - **任务项 6.1.1**：`UserRegisteredEvent` 携带 `userId` / `username` / `nickname` / `phone` / `occurredAt`
    - *测试思路*：构造事件后逐个字段断言；`occurredAt` 来自 `TimeProvider`，用固定时钟断言
  - **任务项 6.1.2**：事件对象是不可变的
    - *测试思路*：反射断言所有字段为 `final` 且无 setter
  - **任务项 6.1.3**：事件中的 `username` 是规范化后的值
    - *测试思路*：传入 `" zhanghao "`，断言事件里是 `"zhanghao"`
- **功能上下文 6.2**：application 层 - 发布时机（这是最容易写错的地方）
  - **任务项 6.2.1**：保存成功后 `publishEvent` **恰好一次**
    - *测试思路*：`verify(publisher, times(1)).publishEvent(any(UserRegisteredEvent.class))`
  - **任务项 6.2.2**：事件中的 `userId` 是落库回填后的 id，不是 `null`
    - *测试思路*：`ArgumentCaptor<UserRegisteredEvent>` 捕获后 `assertThat(captor.getValue().getUserId()).isEqualTo(100L)`
  - **任务项 6.2.3**：发布**必须晚于** `save`（顺序断言）
    - *测试思路*：`InOrder inOrder = inOrder(userRepository, publisher); inOrder.verify(userRepository).save(any()); inOrder.verify(publisher).publishEvent(any());`
  - **任务项 6.2.4**：查重命中（失败路径）**不得发布事件**
    - *测试思路*：`verify(publisher, never()).publishEvent(any())`
  - **任务项 6.2.5**：`save` 抛异常时**不得发布事件**
    - *测试思路*：`when(userRepository.save(any())).thenThrow(new RuntimeException("db down"))`，断言异常冒泡且 `verify(publisher, never()).publishEvent(any())`
- **功能上下文 6.3**：adapter 层 - `WelcomeNotifyListener`（欢迎站内信）

## 架构与重构思考

### 组件间关系分析

```text
RegisterController
      │  （只做协议转换：JSON ↔ RegisterRequest ↔ RegisterCommand）
      ▼
RegisterApplicationService ──发布──▶ UserRegisteredEvent
      │                                    │
      │ 依赖三个「出站端口」                ▼
      ├──▶ UserRepository（接口）      WelcomeNotifyListener
      ├──▶ PasswordEncoder（接口）     AuditLogListener
      └──▶ TimeProvider（接口）              （互不感知）
                 ▲
                 │ 实现
      MyBatisUserRepository / BCryptPasswordEncoderAdapter / SystemTimeProvider
```

**依赖方向的铁律**：`domain` 不 import 任何框架。`UserRepository`、`PasswordEncoder`、`TimeProvider`
这三个接口**定义在 domain 层**，实现在 infrastructure 层 —— 这就是依赖倒置，也是"领域层能被毫秒级单测"的前提。

### 可能存在的耦合点

1. **`RegisterApplicationService` 变成"上帝编排者"**。注册成功后还要发券、送积分、加成长值时，会把越来越多逻辑堆进来。
   → 方向：**用领域事件继续外挂**，Service 只负责"落库 + 发一个事件"，其余全部下沉为监听器。
2. **`TimeProvider` 若被绕过**。只要有人在某处写了 `LocalDateTime.now()`，"券过期""注册时间"这类断言就会变成 flaky 测试（偶尔红、偶尔绿）。
   → 方向：**加一条 ArchUnit 规则**禁止 `domain` 与 `application` 包直接使用 `LocalDateTime.now()` / `Instant.now()` / `UUID.randomUUID()`。
3. **`RegistrationRejectedException` 与现有 `BizException` 的关系**。`mall-auth` 是独立模块，若之后要并入网关统一错误响应，需要一层薄适配。
   → 方向：在 adapter 层的 `GlobalExceptionHandler` 里做映射，**不要把 shop 的 `Result` 直接搬进 domain**。
4. **`UserDO` 与领域 `User` 的映射**。MyBatis 直连领域对象会让 `domain` 被迫带上 `@TableField` 之类的框架注解，污染领域层。
   → 方向：infrastructure 层维护一个贫血的 `UserDO` + `UserConverter`，**领域对象保持纯净**。

### 架构对上下文划分的影响

| 为什么要这样分 | 说明 |
|---|---|
| 为什么把 `Username` 单独做成值对象，而不在 Service 里 `if` 校验 | 校验规则**只写一遍**，Controller、Service、定时任务、批量导入都自动受保护；失败了也只在值对象上测，不用起 Spring |
| 为什么 `PasswordEncoder` 是 domain 端口而不是直接 `new BCryptPasswordEncoder()` | 前者让 application 层测试可以用假实现（毫秒级、结果可预测）；后者会让每次测试真的算 BCrypt（约 100ms/次，循环里会明显卡） |
| 为什么引入 `TimeProvider` 而不是 `LocalDateTime.now()` | "注册时间""券过期"这类需求若依赖真实时间，测试只能在特定时刻通过，属于 flaky 测试 |
| 为什么事件在**落库之后**发布 | 事件里要带自增 id。若在落库前发布，监听器拿到 `null` 的 userId，写的站内信就成了孤儿数据 |
| 为什么观察者要各自 try-catch | Spring 的事件默认**同步**调用，监听器抛出的异常会直接冒泡到主流程，导致"注册明明成功了却返回 500" |
| 为什么把"重复用户名"的最终防线放在数据库 UNIQUE 索引 | 应用层 `exists + insert` 之间存在并发窗口，两个请求可能同时通过查重。数据库唯一索引是唯一可靠的兜底 |

### 测试通过后的重构方向

1. **值对象批量复用的基类**。`Username` / `Nickname` 的"非空 + trim + 长度"逻辑高度重复 → 抽一个 `StringValueObject` 抽象基类或工具方法。**但要在测试全绿后再抽**，否则你无法确认重构没有改变行为。
2. **校验规则从"硬编码 if"升级为可组合的规格（Specification）**。当规则从 3 条涨到 10 条（禁用词、保留字、长度按渠道不同），`if` 会失控。届时引入 `UsernameSpecification` 组合器，每加一条规则只加一个类 + 一批测试。
3. **把"注册"与"登录"共用的部分抽出**。`Username`、`RawPassword`、`PasswordHash`、`PasswordEncoder`、`UserRepository` 在登录用例里会原样复用 —— 这也是**先做注册再做登录**的好处：登录阶段可以纯靠组合已有积木，几乎不用写新的值对象。
4. **`BusyUsername` 检查下沉**。若出现"敏感词用户名"需求，把规则做成 domain 层可测试的独立服务，而不是塞进 Controller 的 `@Pattern` 注解 —— 注解里的正则是**测不到边界**的。
