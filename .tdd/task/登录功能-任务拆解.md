## 需求概述

在 b2c 商城的 `mall-auth` 服务中实现前台买家的「用户名 + 密码」**登录**。用户提交用户名与密码，系统校验输入合法性后从仓储按用户名取出账号，依次判定「账号是否存在 → 账号是否被禁用 → 密码是否匹配」，全部通过则签发一个不透明令牌（token，默认 30 分钟有效、可主动失效）并返回给调用方；同时通过领域事件触发登录审计日志、最后登录时间与登录次数的更新。**任何失败路径都不得签发令牌、不得发布事件、不得改动登录计数。**

### 输入需求（原文）

```text
在 b2c 商城的 mall-auth 服务中实现前台买家的「用户名 + 密码」登录，具体包括：
1. 用户通过 HTTP 接口提交用户名与密码；
2. 用户名/密码为空、或格式非法（长度、字符集）时，直接拒绝并给出明确提示；
3. 「用户名不存在」「密码错误」「账号被禁用」三种情况必须能区分，给出不同提示；
4. 登录必须用 BCrypt 比对密码，绝不比对明文；比对失败不得签发令牌；
5. 校验通过后签发一个不透明 token（默认 30 分钟有效、可主动失效）并返回给调用方；
6. 登录成功后需要记录登录日志、更新最后登录时间、累加登录次数（副作用，用观察者/事件解耦）；
7. 任何失败路径都不得签发令牌、不得写日志、不得改动登录计数。
如有不清晰的内容使用交互式问答让我解释。
```

### 输入架构（原文）

```text
Spring Cloud Alibaba 微服务项目 b2c_mall 中的独立模块 mall-auth
（Spring Boot 2.7.18 / Java 8，端口 8082）。模块内采用四层结构：

- adapter/web    ：LoginController + LoginRequest DTO，只做协议转换，不含业务判断
- application    ：LoginApplicationService 编排用例（认证、签发令牌、发布事件、调用出站端口）
- domain         ：领域模型与规则（Username、RawPassword、PasswordHash、Token、User 聚合根、
                   UserStatus；UserRepository / PasswordEncoder / TokenIssuer / TokenStore /
                   TimeProvider 出站端口；LoginRejectedException 领域异常），
                   纯 Java，零 Spring / 零 MyBatis 依赖
- infrastructure ：实现 domain / application 定义的出站端口（MyBatisUserRepository、
                   BCryptPasswordEncoderAdapter、InMemoryTokenStore）

依赖方向：adapter、infrastructure → application → domain。
密码以 BCrypt 哈希存储，登录时用 matches 比对；令牌是不透明随机串，并入微服务后存 Redis。
```

## 功能点 1：合法账号密码可以完成登录（主成功路径）

- **功能上下文 1.1**：domain 层 - 值对象 `Username`（用户名的合法性由类型本身保证，一旦构造成功即合法）
  - **任务项 1.1.1**：`Username` 拒绝 `null`、空串、纯空白串
    - *测试思路*：`assertThatThrownBy(() -> new Username("  ")).isInstanceOf(IllegalArgumentException.class).hasMessageContaining("用户名")`；`null` 与 `""` 各写一个用例，验证抛出的都是 `IllegalArgumentException` 而不是 `NullPointerException`
  - **任务项 1.1.2**：`Username` 长度边界为 4~20（含两端）
    - *测试思路*：**边界四连测** —— 3 位抛异常、4 位通过、20 位通过、21 位抛异常。这是"验证 Fail/Pass 边界"的典型：两侧各越界一格，中间各取一位
  - **任务项 1.1.3**：`Username` 只接受字母、数字、下划线
    - *测试思路*：`"zhang hao"`（空格）、`"张三"`（中文）、`"zh@ng"`（符号）三种各断言抛 `IllegalArgumentException`
  - **任务项 1.1.4**：`Username` 构造时自动 trim 前后空白
    - *测试思路*：`assertThat(new Username("  zhanghao  ").value()).isEqualTo("zhanghao")` —— 断言的是"规范化后的值"，而不是"原样保留"
  - **任务项 1.1.5**：`Username` 具备值语义
    - *测试思路*：同值两个对象 `isEqualTo` 为真、`hashCode` 相等；并断言放进 `HashMap` 能按 key 取回（**只覆写 equals 不覆写 hashCode 会在这里红**）
- **功能上下文 1.2**：domain 层 - 值对象 `RawPassword`（本次登录提交的明文密码，生命周期极短）
  - **任务项 1.2.1**：`RawPassword` 拒绝 `null` 与空串
    - *测试思路*：两种输入各断言抛 `IllegalArgumentException`
  - **任务项 1.2.2**：`RawPassword` 长度边界为 6~32
    - *测试思路*：5 位抛异常、6 位通过、32 位通过、33 位抛异常
  - **任务项 1.2.3** ◇：`RawPassword` 无任何可以修改内部状态的方法
    - *测试思路*：用反射断言类中不存在 `setXxx` 开头的公开方法，且字段均为 `final`
  - **任务项 1.2.4** ★：`RawPassword` 的 `toString()` **不得泄露明文**
    - *测试思路*：`assertThat(new RawPassword("abc123").toString()).doesNotContain("abc123")` —— 这条是安全断言。登录比注册更容易把密码打进日志（"登录失败，参数：xxx"），所以这条在登录场景下更值得写
- **功能上下文 1.3**：application 层 - `LoginApplicationService` 主成功路径
  - **任务项 1.3.1**：认证通过时"生成 + 保存令牌"各**恰好发生一次**
    - *测试思路*：`verify(tokenIssuer, times(1)).issue(any())` 与 `verify(tokenStore, times(1)).save(any(), any())`。生成与保存是两个端口，两个都要断言
  - **任务项 1.3.2**：返回结果表示成功，且**携带的令牌就是签发出来的那一个**
    - *测试思路*：`assertThat(result.success()).isTrue()`；`assertThat(result.token().value()).isEqualTo(stubbedToken.value())`。注意应用层返回的是协议中立的 `LoginResult`（`success` / `token` / `message`），**不含 HTTP 业务码** —— 业务码是 web 层的事，见 1.4.1
  - **任务项 1.3.3**：签发给令牌的账号身份里 `userId` 来自**仓储查出的** `User`，不是命令里的
    - *测试思路*：`ArgumentCaptor<LoginUser>` 捕获，断言 `getUserId()` 等于桩数据里的 `100L`（命令里根本没有 id，这条能钉死"别自己编 id"）
  - **任务项 1.3.4** ★：主流程**不自己更新登录状态** —— 登录计数、最后登录时间交给观察者
    - *测试思路*：`verify(userRepository, never()).touchLogin(any(), any())`。这条是**架构断言**：一旦有人图省事在 Service 里直接改计数，观察者模式就名存实亡
- **功能上下文 1.4**：adapter/web 层 - `LoginController`
  - **任务项 1.4.1**：`POST /auth/login` 接收 JSON，返回 HTTP 200 + 业务码 200
    - *测试思路*：`mockMvc.perform(post("/auth/login").contentType(APPLICATION_JSON).content(json)).andExpect(status().isOk()).andExpect(jsonPath("$.code").value(200))`
  - **任务项 1.4.2**：请求体 JSON 中的字段能正确映射到 `LoginRequest`
    - *测试思路*：用 `ArgumentCaptor` 捕获传给 Service 的 `LoginCommand`，断言 `username` / `password` 与请求体一致（防止字段名拼错，比如 `userName`）
  - **任务项 1.4.3** ◇：进入 Controller 的数据**不做业务判断**，直接交给 Service
    - *测试思路*：用 `@MockBean` 替换 Service 并让它返回"失败"，断言 Controller **原样返回**该失败结果（证明它没有自作主张）

## 功能点 2：用户名或密码为空不让登录

- **功能上下文 2.1**：domain 层 - 校验的归属（规则下沉到值对象，而非散落在 Service）
  - **任务项 2.1.1** ◇：所有输入校验在值对象构造时完成，非法输入**根本构造不出对象**
    - *测试思路*：断言 `new Username("")` 抛异常的同时，也断言 Service 层不存在 `if (StringUtils.isEmpty(...))` 这类分支 —— 用代码评审或 ArchUnit 检查（**可选，需额外引入 `archunit-junit5`**）
- **功能上下文 2.2**：application 层 - 入参守卫与副作用隔离
  - **任务项 2.2.1**：`command` 为 `null` 时立即抛异常，**不得触碰仓储**
    - *测试思路*：`assertThatThrownBy(() -> service.login(null)).isInstanceOf(IllegalArgumentException.class)`，并 `verify(userRepository, never()).findByUsername(any())`
  - **任务项 2.2.2** ★：任何校验失败路径都**不得签发令牌**
    - *测试思路*：`verify(tokenIssuer, never()).issue(any())`；同时 `verify(tokenStore, never()).save(any(), any())`
  - **任务项 2.2.3**：校验失败时**不得调用** `PasswordEncoder.matches`（省掉昂贵的 BCrypt 运算）
    - *测试思路*：`verify(passwordEncoder, never()).matches(any(), any())`
  - **任务项 2.2.4** ★：校验失败时**不得发布事件**
    - *测试思路*：`verify(publisher, never()).publishEvent(any())`
- **功能上下文 2.3**：adapter/web 层 - 参数校验与统一错误响应
  - **任务项 2.3.1**：`LoginRequest` 上用 Bean Validation 注解声明必填约束
    - *测试思路*：缺 `username` 的 JSON 请求返回非 200 业务码，且 `msg` 中含"用户名"
  - **任务项 2.3.2**：`GlobalExceptionHandler` 把 `IllegalArgumentException` 转成统一 `ApiResult(code=500)`
    - *测试思路*：`mockMvc` 请求非法参数，断言 `$.code` 为 500 且 `$.msg` 非空、**不含 Java 堆栈关键字**（如不出现 `java.lang`）

## 功能点 3：账号不存在 / 密码错误 / 账号被禁用 不让登录

- **功能上下文 3.1**：domain 层 - 出站端口 `UserRepository` 的接口语义
  - **任务项 3.1.1** ◇：`UserRepository` 是接口，且 `domain.port` 包内**零框架依赖**
    - *测试思路*：`grep -r "^import org.springframework" mall-auth/src/main/java/com/mall/auth/domain` 结果为空（**可选自动化：ArchUnit**）
  - **任务项 3.1.2**：按用户名查询的方法签名接受 `Username` 值对象而不是 `String`
    - *测试思路*：`assertThat(UserRepository.class.getMethod("findByUsername", Username.class)).isNotNull()`，并断言不存在接受 `String` 的重载（编译期类型安全）
  - **任务项 3.1.3**：查询结果用 `Optional<User>` 表达，而不是可能为 `null` 的 `User`
    - *测试思路*：`assertThat(UserRepository.class.getMethod("findByUsername", Username.class).getReturnType()).isEqualTo(Optional.class)` —— 让"账号不存在"成为类型系统里的正常分支，而不是等着 NPE
- **功能上下文 3.2**：domain 层 - `User` 聚合根与 `UserStatus`（登录视角：账号要能被"重建"并"判断可登录性"）
  - **任务项 3.2.1**：`UserStatus` 只有 `ENABLED` 与 `DISABLED` 两个取值
    - *测试思路*：`assertThat(UserStatus.values()).containsExactly(ENABLED, DISABLED)`
  - **任务项 3.2.2**：`ENABLED` 的账号 `isLoginable()` 为 `true`
    - *测试思路*：`assertThat(user.status().isLoginable()).isTrue()`
  - **任务项 3.2.3**：`DISABLED` 的账号 `isLoginable()` 为 `false`
    - *测试思路*：`assertThat(user.status().isLoginable()).isFalse()`
  - **任务项 3.2.4** ★：`status` 为 `null` 时视为**不可登录**（防御历史数据）
    - *测试思路*：`tb_user.status` 有 `DEFAULT 1`，但 SQLite 里显式插 `NULL` 仍可能落空值 → 断言 `UserStatus.from(null)` 得到 `DISABLED`（或抛异常），**绝不能**得到 `ENABLED`。这条防的是"默认放开"这类危险取向
  - **任务项 3.2.5**：`User` 能从持久化数据重建（登录场景下用户是"已存在"的，不是新建的）
    - *测试思路*：静态工厂 `User.reconstitute(id, username, passwordHash, nickname, avatarUrl, lastLoginTime, loginCount, status)` 重建后，逐个字段断言；`nickname` / `avatarUrl` 为 `null` 时也要能重建成功（历史数据允许为空）
  - **任务项 3.2.6** ◇：`User` 不可变，不提供 setter
    - *测试思路*：反射断言字段全 `final`、无 `setXxx` 公开方法。**"登录次数的更新"不通过 setter 完成**，而是交给观察者走独立的仓储方法（见 6.4）
- **功能上下文 3.3**：application 层 - 认证三分支（`LoginApplicationService` 的分支主体）
  - **任务项 3.3.1**：仓储返回空 → `success()` 为 `false`，`message()` 为"账号不存在"
    - *测试思路*：桩 `findByUsername → Optional.empty()`，断言 `assertThat(result.success()).isFalse()` 且 `assertThat(result.message()).isEqualTo("账号不存在")`
  - **任务项 3.3.2**：密码不匹配 → `success()` 为 `false`，`message()` 为"密码错误"
    - *测试思路*：桩 `matches → false`，断言 `result.message()` 为 `"密码错误"`（与 3.3.1 的文案**必须不同**，这正是需求第 3 条）
  - **任务项 3.3.3**：账号被禁用 → `success()` 为 `false`，`message()` 为"账号已被禁用"
    - *测试思路*：桩 `status → DISABLED`，断言 `result.message()` 为 `"账号已被禁用"`
  - **任务项 3.3.4** ★：三种失败路径都**不得签发令牌**
    - *测试思路*：三个用例里各自 `verify(tokenIssuer, never()).issue(any())`
  - **任务项 3.3.5** ★：三种失败路径都**不得发布事件**
    - *测试思路*：三个用例里各自 `verify(publisher, never()).publishEvent(any())`
  - **任务项 3.3.6**：账号被禁用时**不得调用** `PasswordEncoder.matches`（先判状态，后比密码）
    - *测试思路*：`verify(passwordEncoder, never()).matches(any(), any())` —— 被禁用的账号不该再花一次 BCrypt
  - **任务项 3.3.7** ★：认证必须发生在签发令牌**之前**（顺序断言）
    - *测试思路*：`InOrder inOrder = inOrder(userRepository, passwordEncoder, tokenIssuer);` 依次 `verify(userRepository).findByUsername(any())` → `verify(passwordEncoder).matches(any(), any())` → `verify(tokenIssuer).issue(any())`。顺序反了就会出现"令牌先签好、认证才发现密码错"这种泄露路径
  - **任务项 3.3.8** ◇：把「账号不存在」与「密码错误」统一成一句"账号或密码错误"（安全加固：防用户名枚举）
    - *测试思路*：**先改 3.3.1 / 3.3.2 的断言** → 看红 → 再改实现 → 变绿。这条是刻意安排的"需求变更演练"：体验"改需求先改测试"。代价是前端提示变模糊，取舍见文末架构思考
- **功能上下文 3.4**：adapter/web 层 - 认证失败的响应
  - **任务项 3.4.1**：认证失败返回业务码 500 + 明确的 `msg`
    - *测试思路*：`andExpect(jsonPath("$.code").value(500)).andExpect(jsonPath("$.msg").value("密码错误"))`
  - **任务项 3.4.2** ★：认证失败的响应体里**不出现** `token` 字段
    - *测试思路*：`andExpect(jsonPath("$.data").doesNotExist())`（或断言整个响应 JSON 里不含 `"token"` 字样）—— 防"失败了还顺手返回个空令牌占位"

## 功能点 4：密码比对使用 BCrypt，不比对明文

- **功能上下文 4.1**：domain 层 - 值对象 `PasswordHash`（从库中取出的哈希）
  - **任务项 4.1.1**：`PasswordHash` 拒绝 `null` 与空串
    - *测试思路*：两种输入各断言抛 `IllegalArgumentException`
  - **任务项 4.1.2** ◇：`PasswordHash` **不提供任何返回明文的途径**
    - *测试思路*：用反射断言该类只有 `value()`（返回哈希）而无 `raw()` / `plain()` 之类方法（**防倒退设计**）
  - **任务项 4.1.3** ★：`PasswordHash.toString()` 打码
    - *测试思路*：`assertThat(hash.toString()).doesNotContain(hash.value())`，且输出形如 `PasswordHash{***}`
  - **任务项 4.1.4**：`PasswordHash` 具备值语义
    - *测试思路*：同哈希值两对象 `isEqualTo` 为真
- **功能上下文 4.2**：domain 层 - 出站端口 `PasswordEncoder`
  - **任务项 4.2.1**：端口声明 `matches(RawPassword, PasswordHash) -> boolean`
    - *测试思路*：反射断言方法存在，参数与返回类型正确
  - **任务项 4.2.2**：端口签名是领域类型进出，不出现 `String`
    - *测试思路*：断言参数类型列表为 `[RawPassword, PasswordHash]`。一旦退化成 `matches(String, String)`，值对象对明文的保护就在这一层漏了
- **功能上下文 4.3**：application 层 - 比对动作
  - **任务项 4.3.1** ★：`matches` 收到的"明文"来自命令、"哈希"来自**仓储查出的账号**
    - *测试思路*：`ArgumentCaptor<RawPassword>` + `ArgumentCaptor<PasswordHash>`，断言前者是命令里的密码、后者等于桩数据里的哈希（防止"拿命令里的东西和命令里的东西比"，那等于没校验）
  - **任务项 4.3.2** ★：走端口比对，**不自己 `equals`**
    - *测试思路*：`verify(passwordEncoder, times(1)).matches(any(), any())` —— 这条钉死"必须调用比对组件"。只断言"登录失败了"是不够的：一个永远抛异常的实现也能让失败用例变绿
  - **任务项 4.3.3**：认证失败时 `matches` 恰好调用一次（不重试、不重复算）
    - *测试思路*：`verify(passwordEncoder, times(1)).matches(any(), any())`
- **功能上下文 4.4**：infrastructure 层 - BCrypt 适配器
  - **任务项 4.4.1**：同一明文两次 `encode` 结果**不同**（验证加盐）
    - *测试思路*：`assertThat(a.value()).isNotEqualTo(b.value())` —— 真实调用 BCrypt，不使用 mock
  - **任务项 4.4.2**：`matches(明文, 该明文对应的哈希)` 为 `true`
    - *测试思路*：先 `encode` 拿到哈希，再 `assertThat(encoder.matches(raw, hash)).isTrue()`
  - **任务项 4.4.3**：`matches(错误明文, 哈希)` 为 `false`
    - *测试思路*：断言为 `false`（**注意不是抛异常**）
  - **任务项 4.4.4**：哈希长度符合 BCrypt 格式（60 字符、`$2a$` 开头）
    - *测试思路*：`assertThat(hash.value()).hasSize(60).startsWith("$2a$")` —— 防止误把 MD5/明文当哈希

## 功能点 5：登录成功签发令牌

- **功能上下文 5.1**：domain 层 - 值对象 `Token`
  - **任务项 5.1.1**：`Token` 拒绝 `null` 与空串
    - *测试思路*：两种输入各断言抛 `IllegalArgumentException`
  - **任务项 5.1.2**：`Token` 的格式是 32 位十六进制（UUID 去掉横线）
    - *测试思路*：`assertThat(token.value()).hasSize(32).matches("[0-9a-f]{32}")`
  - **任务项 5.1.3** ★：`Token.toString()` **打码**，只露前 8 位
    - *测试思路*：`assertThat(token.toString()).contains(token.value().substring(0, 8)).doesNotContain(token.value())` —— 令牌进日志等于账号被接管，这条和 `RawPassword` 那条是同一个道理
  - **任务项 5.1.4**：`Token` 具备值语义
    - *测试思路*：同值两对象 `isEqualTo` 为真，放进 `HashSet` 只有一个元素
  - **任务项 5.1.5** ★：连续两次生成的 `Token` **不相等**（不可预测性）
    - *测试思路*：`assertThat(generator.next()).isNotEqualTo(generator.next())` —— 用 `UUID.randomUUID()` 天然满足。这条防的是"用 `username + 时间戳` 当令牌"这种能被猜到的实现
- **功能上下文 5.2**：domain 层 - 出站端口 `TokenIssuer` / `TokenStore`
  - **任务项 5.2.1**：`TokenIssuer` 只声明 `issue(LoginUser) -> Token`
    - *测试思路*：反射断言该接口只有 1 个方法，返回类型是 `Token`
  - **任务项 5.2.2**：`TokenStore` 声明 `save(Token, LoginUser)` / `find(Token) -> Optional<LoginUser>` / `remove(Token)`
    - *测试思路*：反射断言三个方法存在；`find` 的返回类型是 `Optional`（和 3.1.3 同一个理由）
  - **任务项 5.2.3** ◇：`TokenStore` 的签名里**不出现任何 Redis / Spring 类型**
    - *测试思路*：断言参数类型列表里不含 `StringRedisTemplate`、`RedisTemplate` 等；实现换成内存版还是 Redis 版，domain 完全不用改
- **功能上下文 5.3**：application 层 - 签发时机
  - **任务项 5.3.1**：认证成功后 `issue` 恰好调用一次
    - *测试思路*：`verify(tokenIssuer, times(1)).issue(any())`
  - **任务项 5.3.2** ★：返回值里的 token **就是** `issue` 的返回值
    - *测试思路*：桩 `when(tokenIssuer.issue(any())).thenReturn(new Token("0123456789abcdef0123456789abcdef"))`，断言 `result.getData()` 等于这个字符串。切断"自己拼一个看起来像令牌的字符串"的可能
  - **任务项 5.3.3** ★：签发必须**晚于**认证（与 3.3.7 同源，此处从"令牌"视角再钉一次）
    - *测试思路*：`InOrder inOrder = inOrder(passwordEncoder, tokenIssuer);` 先 `verify(passwordEncoder).matches(...)`，再 `verify(tokenIssuer).issue(...)`
- **功能上下文 5.4**：infrastructure 层 - 令牌存储适配器
  - **任务项 5.4.1**：存入后能按令牌取回同一份身份信息
    - *测试思路*：`store.save(token, user); assertThat(store.find(token)).contains(user)`（或逐字段断言 userId / username）
  - **任务项 5.4.2**：取一个从未签发过的令牌 → 返回 `Optional.empty()`
    - *测试思路*：`assertThat(store.find(new Token("0".repeat(32)))).isEmpty()`
  - **任务项 5.4.3**：`remove` 之后取不回（主动失效 = 退出登录的前提）
    - *测试思路*：`store.remove(token); assertThat(store.find(token)).isEmpty()`
  - **任务项 5.4.4** ★：超过 TTL 后取不回，且**不靠 `Thread.sleep` 实现**
    - *测试思路*：`InMemoryTokenStore` 注入 `TimeProvider`（假时钟），存令牌后把时钟往前拨 31 分钟，断言 `find` 为空。**用真实 `sleep` 写这条测试会让你整套测试慢 30 分钟** —— 这是"注入时间"这条纪律的最好教材
  - **任务项 5.4.5** ◇：`TokenStore` 的实现可以在内存版与 Redis 版之间替换，而 application 层测试**一行不改**
    - *测试思路*：把内存实现换成 Redis 实现（或在测试里换成另一个假实现），`LoginApplicationServiceTest` 保持全绿。这条验证的是"面向端口编程"本身

## 功能点 6：登录成功触发副作用（观察者 / 事件解耦）

- **功能上下文 6.1**：domain 层 - 领域事件 `UserLoggedInEvent`
  - **任务项 6.1.1**：事件携带 `userId` / `username` / `ip` / `device` / `occurredAt`
    - *测试思路*：构造事件后逐个字段断言
  - **任务项 6.1.2** ◇：事件对象是不可变的
    - *测试思路*：反射断言所有字段为 `final` 且无 setter
  - **任务项 6.1.3**：事件中的 `username` 是规范化后的值
    - *测试思路*：传入 `" zhanghao "`，断言事件里是 `"zhanghao"`
  - **任务项 6.1.4** ★：事件中的 `occurredAt` 来自注入的 `TimeProvider`
    - *测试思路*：固定时钟下构造，断言等于该值；**并断言连续两次构造在同一固定时钟下时间相同**（证明没偷用 `LocalDateTime.now()`）
- **功能上下文 6.2**：application 层 - 发布时机（这是最容易写错的地方）
  - **任务项 6.2.1**：认证成功后 `publishEvent` **恰好一次**
    - *测试思路*：`verify(publisher, times(1)).publishEvent(any(UserLoggedInEvent.class))`
  - **任务项 6.2.2** ★：事件中的 `userId` 不为 `null`，且等于查出的账号 id
    - *测试思路*：`ArgumentCaptor<UserLoggedInEvent>` 捕获后 `assertThat(captor.getValue().getUserId()).isEqualTo(100L)`
  - **任务项 6.2.3** ★：发布必须**晚于**认证
    - *测试思路*：`InOrder inOrder = inOrder(passwordEncoder, publisher);` 先 `matches` 再 `publishEvent`
  - **任务项 6.2.4** ★：认证失败（三分支）**不得发布事件**（与 3.3.5 同源，此处从"事件"视角再钉一次）
    - *测试思路*：`verify(publisher, never()).publishEvent(any())`
  - **任务项 6.2.5** ★：签发令牌抛异常时**不得发布事件**
    - *测试思路*：桩 `tokenIssuer.issue` 抛 `RuntimeException`，断言异常冒泡且 `verify(publisher, never()).publishEvent(any())`。**这条最容易被忽略**：顺序写反（先发事件后签令牌）时，就会出现"日志记了登录成功，但用户其实没拿到令牌"
- **功能上下文 6.3**：adapter 层 - `LoginLogListener`（登录审计日志）
  - **任务项 6.3.1**：收到事件后向 `LoginLogRepository` 插入**恰好一条**日志
    - *测试思路*：`verify(loginLogRepository, times(1)).insert(any())`
  - **任务项 6.3.2**：日志内容含 ip 与 device，`userType` 为 `buyer`
    - *测试思路*：`ArgumentCaptor` 捕获后逐个断言；ip / device 为 `null` 时也要能写入（请求可能没有 `User-Agent`）
  - **任务项 6.3.3** ★：写日志失败时**不影响主流程**
    - *测试思路*：桩 `insert` 抛异常，`assertThatCode(() -> listener.on(event)).doesNotThrowAnyException()`
- **功能上下文 6.4**：adapter 层 - `LoginCountListener`（最后登录时间 + 登录次数）
  - **任务项 6.4.1**：收到事件后把账号的累计登录次数 +1
    - *测试思路*：`verify(userRepository, times(1)).increaseLoginCount(any())`
  - **任务项 6.4.2** ★：最后登录时间用的是**事件里的** `occurredAt`，不是 `LocalDateTime.now()`
    - *测试思路*：`ArgumentCaptor<LocalDateTime>`（或捕获更新命令对象），断言等于事件里的固定时钟值。**这是登录功能里最容易 flaky 的地方**
  - **任务项 6.4.3** ◇：两个监听器**互不感知**（新增第三个监听器不需要改前两个）
    - *测试思路*：整体断言 —— 注册两个监听器后 `publishEvent` 一次，分别 `verify` 各自被调用一次；这条本质是"观察者模式的解耦性"测试
  - **任务项 6.4.4** ★：任一监听器抛异常，`LoginApplicationService.login` 仍然正常返回成功
    - *测试思路*：用真实的 `ApplicationEventPublisher`（`@SpringBootTest`）发布事件，断言 Service 返回值不受影响

## 架构与重构思考

### 组件间关系分析

```text
LoginController
      │  （只做协议转换：JSON ↔ LoginRequest ↔ LoginCommand）
      ▼
LoginApplicationService ──发布──▶ UserLoggedInEvent
      │                                    │
      │ 依赖五个「出站端口」                  ▼
      ├──▶ UserRepository（接口）      LoginLogListener（写审计日志）
      ├──▶ PasswordEncoder（接口）     LoginCountListener（改计数/时间）
      ├──▶ TokenIssuer（接口）               （互不感知）
      ├──▶ TokenStore（接口）
      └──▶ TimeProvider（接口）
                 ▲
                 │ 实现
      MyBatisUserRepository / BCryptPasswordEncoderAdapter
      InMemoryTokenStore / SystemTimeProvider
```

**依赖方向的铁律**：`domain` 不 import 任何框架。这五个接口**定义在 domain 层**，实现在 infrastructure 层 ——
这就是依赖倒置，也是"领域层能被毫秒级单测"的前提。

### 可能存在的耦合点

1. **`LoginApplicationService` 变成"上帝编排者"**。登录成功后还要送积分、更新成长值、推送风控时，逻辑会越堆越多。
   → 方向：**用领域事件继续外挂**，Service 只负责"认证 + 签发 + 发一个事件"，其余全部下沉为监听器。
2. **`TokenStore` 是本次最可能"漏框架"的地方**。一旦端口签名里出现 `StringRedisTemplate`，
   `domain` 就被污染了，application 层测试必须起 Redis 容器，反馈从毫秒变秒级。
   → 方向：端口只用 `Token` / `LoginUser` 领域类型；Redis 版实现留在 `infrastructure/token`。
3. **`TimeProvider` 若被绕过**。只要有人在某处写了 `LocalDateTime.now()`，"最后登录时间"这类断言就会变成
   flaky 测试（偶尔红、偶尔绿）。
   → 方向：**加一条 ArchUnit 规则**禁止 `domain` 与 `application` 包直接使用 `LocalDateTime.now()` /
   `Instant.now()` / `UUID.randomUUID()`。
4. **"账号不存在"与"密码错误"提示是否要区分**（任务项 3.3.8 的取舍）。
   区分对用户友好、和 `shop` 现状一致；但会被用来**枚举用户名**（撞库第一步就是确认哪些账号存在）。
   → 方向：对外统一成"账号或密码错误"，把真实原因**只写进审计日志**。
   这次先按"区分"实现（对齐需求原文），把统一化作为一次独立的重构练习 —— 这也是**唯一一次允许你先改测试再改实现**的机会。
5. **`UserDO` 与领域 `User` 的映射**。MyBatis 直连领域对象会让 `domain` 被迫带上 `@TableField` 之类的框架注解。
   → 方向：infrastructure 层维护一个贫血的 `UserDO` + `UserConverter`，**领域对象保持纯净**。

### 架构对上下文划分的影响

| 为什么要这样分 | 说明 |
|---|---|
| 为什么把 `Username` / `RawPassword` 单独做成值对象，而不在 Service 里 `if` 校验 | 校验规则**只写一遍**，Controller、Service、定时任务、批量导入都自动受保护；失败了也只在值对象上测，不用起 Spring |
| 为什么 `PasswordEncoder` 是 domain 端口而不是直接 `new BCryptPasswordEncoder()` | 前者让 application 层测试可以用假实现（毫秒级、结果可预测）；后者会让每次测试真的算 BCrypt（约 100ms/次，循环里会明显卡） |
| 为什么 `TokenIssuer` 与 `TokenStore` 拆成两个端口 | **生成**和**保存**是两件事：生成策略可能换（UUID → JWT）、保存介质也会换（内存 → Redis）。拆开后可以只换一半 |
| 为什么 `Token` 要有 `toString()` 打码这类"看着没用"的测试 | 日志泄露令牌等于账号被接管。断言写进测试，等于给这个设计加了一把锁 |
| 为什么引入 `TimeProvider` 而不是 `LocalDateTime.now()` | "最后登录时间""令牌过期"若依赖真实时间，测试只能在特定时刻通过，属于 flaky 测试；而且 5.4.4 那条 TTL 用例根本没法在合理时间内跑完 |
| 为什么认证顺序必须"查账号 → 判状态 → 比密码 → 签令牌 → 发事件" | 每一步都在排除一类风险：先查再比避免无谓 BCrypt；先比再签避免"先发令牌后认证"的泄露路径；先签再发事件避免"日志说成功、用户没拿到令牌" |
| 为什么观察者要各自 try-catch | Spring 事件默认**同步**调用，监听器抛出的异常会直接冒泡到主流程，导致"登录明明成功了却返回 500" |
| 为什么把登录计数交给观察者而不是 Service 直接写 | 注册与登录会共用同一批副作用（审计日志、计数）。放在主流程里，共用就变成复制粘贴；放在观察者里，新增一种登录方式（手机号、扫码）时一行都不用改 |

### 测试通过后的重构方向

1. **值对象批量复用的基类**。`Username` / `Token` 的"非空 + trim + 长度"逻辑高度重复 → 抽一个 `StringValueObject` 抽象基类或工具方法。**但要在测试全绿后再抽**，否则你无法确认重构没有改变行为。
2. **把失败原因从"返回文案"升级为"错误码枚举"**。现在用中文文案当返回值，一旦要国际化或多端展示就会崩。届时引入 `LoginFailureReason` 枚举，文案在 adapter 层拼。
3. **`Token` 从随机串升级为可自校验令牌**。当调用方要求"网关不查 Redis 也能验签"时，把 `TokenIssuer` 的实现换成 JWT，`Token` 值对象与端口签名都不用改 —— 这就是 5.2 那个端口抽象的红利。
4. **登录失败次数限制**。连续 N 次密码错误锁定 M 分钟，属于典型的"规则密集"逻辑：做成 domain 层可测试的独立服务（依赖 `TimeProvider` 与仓储），**不要塞进 Controller**。
5. **补充"登录成功"与"登录失败"都要写审计日志**。当前只有成功路径发事件；失败路径的日志需要另加一个事件或把失败原因带进事件（注意别把密码带进去）。

## 附：与 shop 模块既有实现的对照（仅供参考，不要直接复制）

`shop` 模块里已有一份登录实现，可作为**读物**对照，但 `mall-auth` 要独立实现一遍：

| 参考文件 | 可借鉴的点 | 本需求的差异 |
|---|---|---|
| `shop/src/main/java/com/shop/service/MallAuthService.java` | `login()` 的分支顺序（空值 → 不存在 → 禁用 → 密码）、`publishEvent` 的用法 | 本需求要求把校验下沉到**值对象**、把令牌抽出 `TokenIssuer`/`TokenStore` 两个端口，Service 里不写 `if` 校验 |
| `shop/src/main/java/com/shop/service/TokenService.java` | 不透明令牌 + 30 分钟 TTL + 滑动续期、日志里对令牌打码 | 本需求把令牌抽象成 `Token` 值对象 + `TokenStore` 端口；测试用**内存实现 + 假时钟**，不连真 Redis |
| `shop/src/main/java/com/shop/observer/AuditLogObserver.java` | 审计日志字段（ip / device / userType / status） | 本需求要在 `com.mall.auth.adapter.listener` 下独立实现，且**写失败要吞掉异常** |
| `shop/src/main/java/com/shop/observer/UserStatusObserver.java` | "更新最后登录时间 + 累加登录次数"由观察者做 | 同上；`shop` 里它依赖 `AccountStoreResolver` 是为了兼容前后台两套表，本模块只有买家一种账号，不需要这层解析 |
| `shop/src/main/java/com/shop/event/UserLoginEvent.java` | 事件载荷字段 | 本需求要求事件对象**不可变**（`shop` 那份是 `@Data`，会生成 setter） |
| `shop/src/main/java/com/shop/dto/LoginUser.java` | 令牌里存什么（id / username / avatarUrl，**不含密码**） | 本需求把它定义在 `application` 层，并靠 4.1.2 那条反射断言保证"拿不到明文密码" |
| `shop/src/main/java/com/shop/common/Result.java` | `code` / `msg` / `data` 的响应约定 | 本模块自己写一份 `ApiResult`，**不要 import shop 的类** |
| `sql/tb_user-ddl.sql` | `tb_user` 表结构（`status` 默认 1、`login_count` 默认 0） | 本模块用自己的临时库，**绝不要动 `shop.db`** |
| `shop/src/main/java/com/shop/controller/MallAuthController.java` | 接口路径风格 `/mall/auth/login` | 本模块用 `/auth/login`（网关 `StripPrefix=1` 会剥掉前缀） |

> **一句话**：`shop` 的实现是"能跑就行"，`mall-auth` 这次要的是"每一行都有测试撑着、每一层都换得掉"。对照着读，但别抄。
