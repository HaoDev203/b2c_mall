# 功能点 1 · 顶部筛选 11 项（O01~O11，11 条）

## O01 · 订单编号精确匹配 ★★

- **测试方法**：`should_search_by_order_no_exactly`
- **对应需求**：「订单编号：支持**精确输入**订单号检索」
- **前置**：`orderNo = "SO202610230001"`；库里有 `SO202610230001` 和 `SO2026102300019`
- **断言**：
  - 传入完整订单号 → 返回 **1 条**，`orderNo` 完全相同
  - 传入**前缀** `"SO202610"` → 返回 **0 条**
- **红在哪**：`OrderMapper.selectPage` 用 `LIKE '%'||?||'%'` → 断言红（前缀也能查到）
- **陷阱（这是本期最重要的修正）**：一期末 shop 后台订单查询**就是 `LIKE` 模糊匹配**，而需求写的是「精确」。这是审计出的真实缺口，改一行 SQL 就能修
- **必须用真 SQL 验**：Mock 只能证明参数透传，证明不了 `=` 还是 `LIKE`。这条**必须配一个真库探针**：插两条前缀相同的订单，查前缀应返回 0 条
- **为什么 ★★**：需求原文专门加了「精确」二字，而现有代码是模糊的 —— 这是最能体现「TDD 补出真实缺口」的一条

## O11 · 下单时间区间

- **测试方法**：`should_filter_by_create_time_range`
- **对应需求**：「下单时间：开始日期～结束日期」
- **前置**：`startDate = "2026-10-01"`、`endDate = "2026-10-23"`
- **断言**：
  - Mapper 收到两个日期参数
  - SQL 用 `date(create_time) >= ? AND date(create_time) <= ?`
- **红在哪**：区间参数不存在 → 编译红
- **陷阱（关键）**：
  - **区间是闭区间**（含首尾两天）。写成 `>` / `<` 会漏掉整天的数据
  - **`create_time` 带时分秒**，必须 `date(create_time)` 截断比较，否则 `2026-10-23 10:00` 会大于 `2026-10-23`（字符串比较 `"2026-10-23 10:00" > "2026-10-23"` 为真）→ 结束日当天一单都查不到
  - 只传开始不传结束 / 反之，要能单独生效（另写两条边界）

# 功能点 2 · 快捷时间与组合筛选（O12~O13，2 条）

## O12 · 快捷时间换算（今日 / 昨日 / 近 7 天 / 近 30 天）

- **测试方法**：`should_resolve_quick_date_range`（`@ParameterizedTest`，4 组）
- **对应需求**：「内置快捷选项：今日、昨日、近 7 天、近 30 天」
- **前置**：固定「今天」= `2026-10-23`（用 `Clock` 注入固定时钟，**不要用 `LocalDate.now()`**）
- **断言**：

  | 快捷项 | 期望 start | 期望 end |

  | 今日 | 2026-10-23 | 2026-10-23 |
  | 昨日 | 2026-10-22 | 2026-10-22 |
  | 近 7 天 | 2026-10-17 | 2026-10-23 |

- **陷阱**：

  - **不能用 `LocalDate.now()`**，测试会随运行日期变化。必须注入 `Clock`（这是 24 条里唯一需要时间可控的地方）

# 功能点 3 · 状态快捷标签栏（O14，1 条）

## O14 · 7 个 Tab 各自计数 ★

- **测试方法**：`should_return_count_for_seven_tabs`
- **对应需求**：「快捷筛选标签：全部、待付款、待发货、待收货、交易成功、交易失败、待成团」
- **前置**：6 个状态各桩不同值，`countByStatus(shopId, null)` 桩成 **999（故意不一致）**
- **断言**：
  - 返回 7 个 key：`all, pendingPay, pendingShip, pendingReceive, success, failed, pendingGroup`
  - `all` = 6 个状态**之和**（不是 999）
  - 每个 Tab 的值等于对应桩值
- **红在哪**：`PENDING_GROUP` 状态不存在 → 编译红
- **陷阱**：
  - 和 U02 同理：**「全部」= 各状态之和，不是 `COUNT(*)`**。桩值必须不一致才能逼出差异
  - **6 个状态 + 「全部」= 7 个 Tab**，容易数错成「7 个状态 + 全部」
  - 每个 Tab 一次查询 = 6 次 count + 1 次 list。可以优化成 `GROUP BY status` 一次查完，但那是**重构阶段**的事，第一次实现老老实实 6 次

# 功能点 4 · 每行订单展示（O15~O17，3 条）

## O15 · 「共 N 件」= 明细数量合计 ★

- **测试方法**：`should_compute_total_quantity_from_order_items`
- **对应需求**：「实付金额…标注**共 N 件**」
- **前置**：订单有 2 条明细 —— 商品 A × `quantity=1`、商品 B × `quantity=8`
- **断言**：`totalQuantity == 9`（不是 2）
- **红在哪**：返回对象无 `totalQuantity` → 编译红
- **陷阱（最容易错）**：**N = 数量之和，不是明细行数**。桩数据必须让两者不同（2 行 / 9 件），否则实现写成 `items.size()` 也绿
- **为什么 ★**：需求里「x1 / x8」和「共 N 件」同时出现，正好能把「件数」和「行数」区分开

## O16 · 收件人手机号脱敏 ★

- **测试方法**：`should_mask_receiver_phone`
- **对应需求**：「买家 / 收货人：买家账号、收件人**脱敏**手机号」
- **前置**：`receiverPhone = "13800138000"`
- **断言**：返回的 `receiverPhoneMasked == "138****8000"`
- **红在哪**：返回原号码 → 断言红
- **陷阱**：
  - **脱敏必须发生在后端**，不能把原号码返回给前端让前端遮。前端遮只是视觉效果，F12 一看就有
  - 边界：**null / 空串 / 短于 11 位**都要能处理（返回原值或空串，不抛异常）。另写一条 `should_handle_null_phone_when_masking`
  - 脱敏后**不能再还原**：如果业务需要拨号，应该另给一个「已授权可见」的接口并记审计日志，不能在同一响应里既给脱敏又给原文
- **为什么 ★**：这是需求里唯一的隐私要求，也是后端必须承担、前端替不了的一件事

## O17 · 状态标签（5 种特殊标记）

- **测试方法**：`should_return_status_tags`
- **对应需求**：「标签标记特殊类型：待发货 / 待收货 / 退款申请中 / 电子卡券订单 / 同城配送」
- **断言**（`@ParameterizedTest`，5 组）：

# 功能点 5 · 发货（O18~O21，4 条）

## O18 · 发货时写入物流单号 ★

- **测试方法**：`should_write_tracking_no_when_shipping`
- **对应需求**：「发货：弹出发货弹窗，**填写物流单号**」
- **前置**：`orderId = 1`、`trackingNo = "SF1234567890"`，订单当前 `PENDING_SHIP`
- **断言**：
  - `updateTrackingNo(1L, "SF1234567890")` 被调用一次
  - 状态流转为 `PENDING_RECEIVE`
  - 返回成功
- **红在哪**：`tracking_no` 列不存在 / `ship` 方法没有单号参数 → 编译红
- **陷阱（关键：顺序）**：**先流转状态、成功后再写单号**。反过来会留下「有单号但状态还是待发货」的脏数据 —— 买家看得到运单号，订单却停在待发货，这是最难解释的线上问题
- **为什么 ★**：一期末 shop 的 `OrderController.ship` 只取 `dto.getOrderId()`，`ShipDTO` 里**根本没有单号字段** —— 功能表面能用，数据实际丢失。这是审计出的最扎心一条

---

## O19 · 仅「待发货」可发货

- **测试方法**：`should_reject_ship_when_status_is_not_pending_ship`
- **对应需求**：「发货：**待发货订单才展示该按钮**」
- **前置**：`@ParameterizedTest` 跑 6 个非待发货状态
- **断言**：每个状态都返回失败，`never()` 调用状态流转
- **红在哪**：无状态校验 → 断言红
- **陷阱**：**前端隐藏按钮不是约束**。直接调接口就能绕过，后端必须自己校验。这条和 O18 是一对：O18 证明「能发」，O19 证明「不该发的发不了」

## O21 · 部分失败返回明细，不回滚其他条

- **对应需求**：同上（可观测性）

# 功能点 6 · 数据隔离（O22~O23，2 条）

## O22 · 别家订单不出现在列表

- **测试方法**：`should_not_return_other_shops_orders`
- **对应需求**：权限段「只查看当前登录店铺数据」

### 四处按实测更正的口径

1. **O14 的 `all` 用独立 `COUNT(*)`，不是 6 个状态之和。**
   探针实测 shop1：`countAll = 41`、6 个 Tab 之和 `39`，差的 2 单正是 `REFUNDING`。
   求和会让商家点「全部」看不到正在退款的订单 —— 那恰恰是最需要处理的。
   （与 B3 的 U02 同一结论：买家侧 4 个 Tab 也是 38 vs 36。）

2. **O11 用 `create_time < date(endDate,'+1 day')`，不用 `date(create_time) >= ?`。**
   探针实测：同一天区间取到 2 条（含 `23:59:59`），而 `create_time <= '2026-10-31'` 取到 0 条。
   `date(create_time)` 也能取整天，但在列上套函数会让索引失效 —— 与 B2 的既定原则冲突，
   所以选前者：既保证闭区间，又不牺牲索引。

3. **O18 不拆两步，用一条 UPDATE 同时写状态与单号。**
   拆开（先写单号、再改状态）会留下「有运单号但状态仍是待发货」的中间态：
   买家看得到单号、订单卡在待发货，这是最难解释的线上问题。
   单条 UPDATE 天然原子，比「靠顺序保证」更强。WHERE 里再带一次
   `status = 'PENDING_SHIP'` 兜并发，重复发货影响 0 行。

4. **O08「暂无售后」在库里存 NULL，不是字符串 `'none'`。**
   演示数据与 DDL 注释已一并更正：新订单不写这一列天然就是 NULL，
   不会出现「漏写 `'none'` 就变成未知状态」。筛选时传 `NONE`，Service 翻译成 `IS NULL`。
