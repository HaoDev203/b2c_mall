## C01 · 只返回上架商品

- **测试方法**：`should_only_return_on_sale_products`
- **对应需求**：权限段「只展示状态正常的店铺商品」
- **前置**：`productMapper.selectOnSalePage(...)` 返回 2 条 `status = on_sale` 的商品
- **断言**：
  - 返回列表 size = 2
  - 每条 `status` 都等于 `on_sale`
  - 传给 Mapper 的参数里**不含下架商品的 id**
- **红在哪**：Mapper 方法还不存在（`selectOnSalePage` 未定义）→ 编译红
- **陷阱**：不要写「传入 status 参数让 Service 过滤」。**过滤必须发生在 SQL 里**，Service 层拿到全量再 `stream().filter()` 会把全表捞进内存

## C02 · 分类导航同名去重 ★

- **测试方法**：`should_dedupe_category_navigation_by_name`
- **对应需求**：非功能需求栏「分类名去重」
- **前置**：`categoryMapper.selectAll()` 返回 4 行 ——
  ```
  (id=1, name="数码") (id=7, name="数码")
  (id=2, name="服饰") (id=3, name="食品")
  ```
- **断言**：
  - 返回 size = **3**（不是 4）
  - 「数码」只出现 1 次，且保留的是 **id=1**（首条）
  - 顺序与入参一致（`数码, 服饰, 食品`）
- **红在哪**：`MallCategoryService` 类不存在 → 编译红
- **陷阱**：**不能用 `SELECT DISTINCT *` 或 `DISTINCT name, id`**。两行 id 不同，`DISTINCT *` 一行也去不掉；只选 name 又丢了 id，前端点分类传不回来。必须在 Service 用 `LinkedHashMap<String, Category>` 按 name 保留首条
- **为什么 ★**：这是需求里唯一一条写在「非功能需求」栏的业务规则，老师大概率会问「去重在哪做的、为什么不在 SQL 里」

## C03 · 默认「全部」返回全部上架商品

- **测试方法**：`should_return_all_on_sale_products_when_category_is_absent`
- **对应需求**：导航栏「默认选中【全部】标签」
- **前置**：`categoryId = null`
- **断言**：Mapper 收到的 `categoryId` 为 `null`（`isNull()`），返回全部上架商品，不被任何分类约束
- **红在哪**：`list(...)` 方法签名里还没有 `categoryId` 参数 → 编译红
- **陷阱**：不能把 `null` 当 `0` 传下去。`category_id = 0` 会一条都查不到，「全部」直接变空白页

## C04 · 选某分类只返回该分类商品

- **测试方法**：`should_filter_products_by_category_id`
- **对应需求**：导航栏「点击对应分类标签…只展示该分类下上架商品」
- **前置**：`categoryId = 2L`
- **断言**：`verify(productMapper).selectOnSalePage(eq(2L), any(), any(), any())` 且**同时**仍带 `on_sale` 条件（C01 的约束在筛选后依然生效）
- **红在哪**：同 C03，签名缺失
- **陷阱**：这条要和 C01 一起看 —— 选了分类不代表可以不筛状态。测试里要断言「两个条件同时存在于同一次调用中」，否则实现可能写成「有分类就只按分类查」

## C05 · 按销量排序

- **测试方法**：`should_sort_by_sales_desc`
- **对应需求**：描述段「支持按销量 / 价格排序」
- **前置**：`sort = "sales"`
- **断言**：传给 Mapper 的排序值为 `sales`，且 SQL 里是 `ORDER BY sales DESC`（销量大的在前）
- **红在哪**：排序参数未支持 → 编译红或断言红
- **陷阱**：**排序方向是 DESC 还是 ASC，需求没写**。默认销量取 DESC（卖得多的先露脸是行业惯例），这条要在测试注释里写清「这是我定的口径」，避免答辩时被问「需求没说你怎么定」

- **测试方法**：`should_sort_by_price`
- **对应需求**：同上
- **前置**：`sort = "price"`
- **断言**：传给 Mapper 的排序值为 `price`
- **红在哪**：同 C05

## C07 · 非法排序参数回落默认值（防 SQL 注入）★★

- **测试方法**：`should_fall_back_to_default_sort_when_param_is_illegal`
- **对应需求**：需求未明写，属**非功能安全项**
- **前置**：`sort = "price; DROP TABLE tb_product"`
- **断言**：
  - 传给 Mapper 的排序值 **不等于** 入参原文
  - 等于默认值（如 `id` 或 `create_time`）
  - 表仍然存在（这条只能靠「参数没被拼进 SQL」来保证，测不了 DROP 是否执行）
- **红在哪**：无白名单校验 → 断言红（非法字符串被原样传下去）
- **陷阱**：排序字段**必须是白名单枚举**，不能 `String` 拼接。MyBatis 里排序字段只能用 `${}`（`#{}` 是预编译占位符，放进 `ORDER BY` 会变成 `ORDER BY 'price'` 常量，排序失效）。**`${}` + 用户输入 = 注入漏洞**，白名单是唯一解
- **为什么 ★★**：这是 88 条里唯一一条纯安全断言，也是「TDD 能测出安全漏洞」的最好例子

## C08 · 卡片字段齐备

- **测试方法**：`should_return_all_card_fields`
- **对应需求**：列表「商品主图 / 商品名称 / 商品售价 / 商品销量」
- **前置**：一条完整商品记录
- **断言**：返回对象的 4 个字段都非空 —— `mainImage`、`name`、`price`、`sales`
- **红在哪**：返回 DTO 缺字段（如 `sales` 没映射）→ 断言红
- **陷阱**：**不要断言具体值**（`isEqualTo("商品A")`），这条测的是「字段有没有丢」，不是「值对不对」。值断言会让这条变得脆弱 —— 改个演示数据就红

## C09 · 已下架商品详情不可见

- **测试方法**：`should_not_expose_detail_of_off_sale_product`
- **对应需求**：权限段「只展示状态正常的店铺商品」
- **前置**：`productMapper.selectByIdAndOnSale(9L)` 返回 `null`（该商品已下架）
- **断言**：返回 `code != 200`，提示含「下架」或「不存在」
- **红在哪**：详情接口没有状态校验 → 断言红（返回 200 + 商品数据）
- **陷阱**：「商品不存在」和「商品已下架」**是否要区分**？需求没写。建议**统一返回「商品不存在或已下架」**，避免通过提示语探测别人家下架商品的存在性
- **注意**：这条和 C01 是一对 —— C01 管列表（SQL 过滤），C09 管详情（Service 判断）。**详情是从 id 直接查的，SQL 过滤管不到**，所以必须在 Service 再判一次
