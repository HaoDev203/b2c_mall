## U01 · 只返回当前登录用户的订单 ★

- **测试方法**：`should_only_return_current_user_orders`
- **对应需求**：权限段「只查看当前用户数据」
- **前置**：`UserContext.getUserId()` = `1001`；用户 1002 有 4 单
- **断言**：
  - Mapper 收到 `eq(1001L)`，`never()` 出现 `1002L`
  - 返回列表里每条 `userId == 1001`
- **红在哪**：`MallOrderService` 不存在 → 编译红
- **陷阱**：**userId 只能从 `UserContext` 取，不能从请求参数取**。如果接口允许 `?userId=`，改个参数就能看别人订单 —— 这是最典型的水平越权
- **为什么 ★**：手测永远用自己的账号，越权问题 100% 发现不了

---

## U02 · Tab 计数（4 个状态 + 全部）★

- **测试方法**：`should_return_count_per_status_tab`
- **对应需求**：Tab 栏「待付款 0 / 待发货 9 / 待收货 0 / 已完成 10」
- **前置**：
  - `countByUser(1001, "PENDING_PAY")` → `0L`
  - `countByUser(1001, "PENDING_SHIP")` → `9L`
  - `countByUser(1001, "PENDING_RECEIVE")` → `0L`
  - `countByUser(1001, "SUCCESS")` → `10L`
  - `countByUser(1001, null)` → **`99L`（故意不一致）**
- **断言**：`allCount == 19`（**4 个之和**），`pendingShip == 9`
- **红在哪**：Tab 计数未实现 → 编译红
- **陷阱（关键）**：「全部」= **各状态之和**，还是 `COUNT(*)`？两者在真实数据里通常相等，**测试必须用不一致的桩值才能逼出差异**。这里把「不分状态的总数」桩成 99、各状态之和是 19，实现若偷懒用 `COUNT(*)` 立刻红
- **为什么 ★**：需求给的是 4 个具体数字，`0/9/0/10` 加起来 19。用示例数字当桩值，断言和需求原文能一一对照

## U03 · 订单编号精确检索 ★

- **测试方法**：`should_search_by_order_no_exactly`
- **对应需求**：「按订单号精确检索」
- **前置**：`orderNo = "SO202610230001"`
- **断言**：
  - Mapper 收到 `eq("SO202610230001")`
  - 返回 1 条，`orderNo` 完全相等
- **红在哪**：`selectByUserPage` 无 `orderNo` 参数 → 编译红
- **陷阱**：**必须是 `=`，不是 `LIKE '%...%'`**。一期末 shop 后台订单查询就是 `LIKE`，需求要「精确」，这是审计出的真实缺口
- **这条测不出语义**：Mock 只能证明「参数原样透传」，证明不了 SQL 里是 `=` 还是 `LIKE`。**必须另外用真 SQL 探针验证**：查订单号前缀（如 `SO202610`）应该返回 **0 条**
- **为什么 ★**：需求原文专门加了「精确」两个字，这是唯一一处强调匹配方式的地方

## U04 · 订单卡片字段齐备

- **测试方法**：`should_return_all_order_card_fields`
- **对应需求**：卡片「订单编号 / 店铺名称 / 商品图片 / 商品名称 / 数量 / 单价 / 总额 / 状态 / 支付方式」
- **前置**：1 条订单 + 2 条明细
- **断言** 9 个字段非空：
  ```
  orderNo, shopName, orderItems[].productImage, orderItems[].productName,
  orderItems[].quantity, orderItems[].price, totalAmount, status, payType
  ```
- **红在哪**：返回 DTO 缺 `shopName`（一期末 shop 的 Order 实体没有店铺名，只有 shop_id）→ 断言红
- **陷阱**：
  - **`shopName` 需要 JOIN 或冗余字段**。订单表只有 `shop_id`，要展示店铺名称必须查店铺表或冗余存一份。建议**下单时冗余写入 `shop_name`**（店铺改名不影响历史订单，这也是电商通行做法）
  - **`payType` 只在「待发货」及之后的状态才有值**，待付款订单为空是正常的。断言要按状态区分，不能一刀切要求非空

## U05 · 删除订单 = 软删除 ★★

- **测试方法**：`should_soft_delete_order_not_physically`
- **对应需求**：「删除订单：删除这条订单记录（仅隐藏，后台保留订单数据）」
- **前置**：`is_deleted` 列存在，默认 0
- **断言**：
  - 调用了 `softDeleteByIdAndUser(orderId, userId)`
  - **`verify(orderMapper, never()).deleteByIdAndUser(any(), any())`** —— 物理删除方法一次都没被调用
  - 反射断言：`OrderMapper` 类上**不存在**以 `delete` 开头的方法
- **红在哪**：`is_deleted` 列不存在 / Mapper 无 `softDeleteByIdAndUser` → 编译红
- **陷阱**：只断言「返回成功」是不够的 —— 实现完全可以「先物理删了再返回成功」。必须用 `never()` + 反射断言双保险
- **反射断言的意义**：`never()` 只能证明「这次没调用」，反射能证明「这个类里根本不许有物理删除方法」。后者更彻底 —— 它阻止了未来任何人写出这个危险方法
- **为什么 ★★**：需求原文「仅隐藏，后台保留」是本项目**跨页面一致性要求最强的一条**

---

## U06 · 删除后后台仍可见 ★★

- **测试方法**：`should_keep_order_visible_in_admin_after_buyer_deletes`
- **对应需求**：同上「后台保留订单数据」
- **前置**：订单 1 已被买家软删除（`is_deleted = 1`）
- **断言**：后台 `selectPage(shopId, ...)` 的结果里**仍包含订单 1**
- **红在哪**：后台 `selectPage` 若加了 `is_deleted = 0` 条件 → 断言红
- **陷阱（这条最容易写错）**：买家侧 3 个查询都带 `is_deleted` 条件（列表 / 总数 / 详情），**后台 `selectPage` 刻意不带**。如果为了「统一」给后台也加上，商家就再也看不到被买家删掉的问题订单了 —— 而这恰恰是客诉最需要的
- **为什么 ★★**：这是天生跨页面的规则，**只测买家侧永远抓不到**。必须在同一个测试里同时验证「买家看不到」+「后台看得到」

## U07 · 越权：删不到别人的订单

- **测试方法**：`should_not_delete_other_users_order`
- **对应需求**：权限段「只查看当前用户数据」
- **前置**：`UserContext.userId = 1001`，订单 2 属于用户 1002
- **断言**：
  - `softDeleteByIdAndUser(2L, 1001L)` 影响行数 = **0**
  - 返回失败
  - 订单 2 的 `is_deleted` 仍为 0
- **红在哪**：删除方法没有 userId 条件 → 断言红
- **陷阱**：**越权校验必须写在 SQL 的 WHERE 里**（`WHERE id=? AND user_id=?`），不能「先查出来再判 userId」。后者有 TOCTOU 窗口，且多一次查询
- **另一种写法**：先 `selectByIdAndUser` 查不到就返回失败 —— 也可以，但要保证「查」和「删」用的是同一个 userId 条件

## U08 · 已删订单不出现在买家列表

- **测试方法**：`should_hide_deleted_orders_from_buyer_list`
- **对应需求**：删除 = 「仅隐藏」
- **前置**：用户 1001 共 3 单，其中订单 1 已软删除
- **断言**：
  - `selectByUserPage` 返回 **2** 条
  - `countByUser` 返回 **2**
  - 返回列表里不含订单 1 的 id
- **红在哪**：买家侧查询没加 `is_deleted = 0` → 断言红
- **陷阱**：**列表和总数必须同时过滤**。只改列表不改 total，会出现「列表 2 条但显示共 3 条」的分页错乱。这条要同时断言两个方法

## U09 · 立即购买返回商品可下单信息

- **测试方法**：`should_return_buy_now_info_for_purchasable_product`
- **对应需求**：「立即购买：跳转商品下单页，重新购买该商品」
- **前置**：商品 5 上架、`stock = 10`、`price = 99.00`
- **断言**：返回含 `productId, name, price, stock, status`
- **红在哪**：`buyNow` 方法不存在 → 编译红
- **陷阱**：
  - **必须校验商品仍在售**。已下架/已售罄的商品不能返回可购买信息，否则前端跳过去再报错，体验断层
  - 另补一条断言：「库存为 0 时返回不可购买」（可并入本方法，用 `@ParameterizedTest` 跑「上架有货 / 上架无货 / 已下架」三组）
