每条任务项下方都写了**「红在哪」**，用来在跑测试时核对：如果红的不是预期的那个位置，说明测试本身写错了。

## 四、数据口径（写断言时的既定解释，全 88 条通用）

这几条是**全项目最容易写错的口径**，先在这里定死，后面每份明细不再重复。

| 指标 | 口径 | 为什么不能想当然 |
|---|---|---|
| 「已支付」 | `pay_time IS NOT NULL` | **不用 status 枚举**。订单支付后还会继续流转（待发货→待收货→交易成功），按 status 算会重复或漏算 |
| 「今日」 | `date(pay_time) = 今天` | 按**支付时间**归属，不是下单时间。昨天下的单今天付钱，算今天收入 |
| 「退款金额」 | `status = 'REFUNDING'` 的 `pay_amount` 之和 | 本期没有独立的退款时间列，日期按 `create_time` 归属（这是妥协，答辩要能解释） |
| 「库存预警」 | `stock <= stock_warn` | `stock_warn IS NULL` 的商品**有意不预警**。加 `OR stock_warn IS NULL` 会让所有没配预警线的商品一上架就预警 |
| 「同比」 | `(今日 − 昨日) / 昨日 × 100%` | **昨日为 0 时固定 `100.00`**，不是 0，不是 `∞`，不能抛除零异常。需求原文写死 |
| 「客单价」 | 今日支付总金额 ÷ 今日支付订单数 | 分母为 0 时（今天没单）返回 `0.00`，不是 NaN |
| 「共 N 件」 | 该订单所有明细 `quantity` 之和 | 不是明细行数。买 1 个商品 × 8 件，N = 8 |
| 「分类名去重」 | 按 `name` 保留**首条**，用 `LinkedHashMap` | 不能靠 SQL `DISTINCT *`：同名行 id 不同，去不掉 |
| 「软删除」 | `is_deleted = 1`，**后台仍可见** | 需求原文「仅隐藏，后台保留订单数据」。删了后台就查不到了 |

## 五、明确不做的部分（前端职责，后端测不了）

需求文档是产品视角写的，混了一类「后端拿不到、也不该测」的东西。**必须提前划清，否则答辩被问会语塞。**

| 需求原文 | 归属 | 后端实际交付 |
|---|---|---|
| 卡片图标、数字红色字体 | CSS | 只返回数字与 key |
| 市场价**划线原价** | CSS `text-decoration` | 返回 `marketPrice` 数值 |
| 商品名**文字超长自动截断** | CSS `text-overflow: ellipsis` | 返回完整 `name` 字符串 |
| 折线图**颜色**（蓝=今日/绿=昨日）、Y 轴自动适配、鼠标悬浮提示 | ECharts / 前端 | 返回 2 条 × 24 点的数值数组 |
| 点击卡片跳转详情、唤起聊天窗口、二次确认弹窗 | 前端路由/交互 | 提供 `id`，跳转由前端做 |
| 导出 Excel 的**列宽、颜色、字体** | POI 样式 | 只保证**导出行数与列值正确** |
| 收件人手机号**脱敏展示** | — | **这条是后端**（数据出境前就要脱敏），见 O16 |

> 标准答法：**「截断是 `text-overflow`，图标是 CSS，折线颜色是前端配置项。后端交付的是数据契约，不是像素。」**

## 六、表结构：需求要、一期末 shop 缺的字段

新模块从零建库，不用再 `ALTER TABLE` 打补丁。

| 表 | 新字段 | 对应需求 | 说明 |
|---|---|---|---|
| `tb_product` | `goods_type` | 商品类型：普通/秒杀 | **不叫 `product_type`**。shop 里那个字段装的是「类别」，同名会误导所有人 |
| `tb_product` | `category_kind` | 商品类别：实物/虚拟/卡券 | — |
| `tb_product` | `warehouse_stock` | 仓库库存 | 与门店库存分开 |
| `tb_product` | `store_stock` | 门店库存 | — |
| `tb_product` | `inflated_sales` | 注水销量 | 与真实销量分开返回，**不合并** |
| `tb_product` | `delivery_types` | 配送方式多选 | 逗号分隔（`express,self_pickup`），筛选用 `IN` |
| `tb_order` | `order_type` / `order_category` | 订单类型 / 订单类别 | 两个不同维度 |
| `tb_order` | `logistics_type` / `store_name` | 物流类型 / 门店名称 | — |
| `tb_order` | `tracking_no` | 物流单号 | 发货时写入 |
| `tb_order` | `is_deleted` | 买家删除标记 | 软删除，默认 0 |
| `tb_messages` | `order_no` | 消息携带订单编号 | 点击跳详情 |

**订单状态 7 个**：待付款 / 待发货 / 待收货 / **待成团** / 交易成功 / 交易失败 / 退款中。
一期末 shop 只有 6 个、**缺「待成团」**，这是 O04 / O14 两条的来源。

## 七、批次顺序（按依赖从少到多，不是按页面顺序）

| 批次 | 内容 | 条数 | 为什么排这里 |
|---|---|---|---|
| **B0** | 模块骨架 + DDL + 探针 + jacoco | 1 探针 | 看不到 `Tests run: 1`，后面 88 条都是幻觉 |
| **B1** | C 端商品列表 | 9 | 只依赖商品 + 分类两张表，最简单，先校准节奏 |
| **B2** | 店铺 Dashboard | 23 | 聚合 + 缓存 + 同比，最能体现 TDD 价值 |
| **B3** | C 端订单管理 | 9 | 跨页面规则密集（软删除 vs 后台可见） |
| **B4** | 店铺商品管理 | 23 | 筛选维度多 + 批量操作 |
| **B5** | 订单查询 | 24 | 11 项筛选 + 状态机，最复杂放最后 |

**每批判定标准**（缺一步都不算完成）：

1. 先把本批**全部**测试写完
2. 跑 `mvn -pl mall-tdd test`，**必须编译红或断言红**，且红在每条明细写明的「红在哪」
3. 红的位置不对 → 改测试，不改实现
4. 才写实现，转绿
5. 提交两个 commit：`test(mall-tdd): Bx ...` 在前，`feat(mall-tdd): Bx ...` 在后
