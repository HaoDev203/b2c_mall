# 功能点 1 · 顶部筛选（P01~P07，7 条）

## P01 · 商品名称模糊搜索

- **测试方法**：`should_search_by_name_fuzzy`
- **对应需求**：筛选「商品名称：模糊搜索商品名称关键词」
- **前置**：`keyword = "手机"`
- **断言**：Mapper 收到 `eq("手机")`，SQL 用 `name LIKE '%' || ? || '%'`
- **红在哪**：`ProductQueryService` 不存在 → 编译红
- **陷阱**：**模糊搜索的参数本身不加 `%`**，`%` 由 SQL 拼。如果 Service 里拼成 `"%手机%"` 再传给 SQL，SQL 又拼一层变成 `%%手机%%`（能查但索引失效）

---

## P02 · 商品类型筛选（普通 / 秒杀）

- **测试方法**：`should_filter_by_goods_type`
- **对应需求**：筛选「商品类型：普通商品、秒杀商品等」
- **前置**：`goodsType = "seckill"`
- **断言**：Mapper 收到 `eq("seckill")`，SQL 用 `goods_type = ?`
- **红在哪**：**字段名陷阱** —— 一期末 shop 的 `product_type` 装的是「类别」（实物/虚拟/卡券），不是「类型」。新库必须用 `goods_type`
- **陷阱（必读）**：**如果这条用 `product_type` 实现，测试照样能绿，但语义完全错**。Mock 只验证参数透传，验证不了字段含义。所以测试里要把字段名写进方法名/注释：`should_filter_by_goods_type_not_product_type`

---

## P03 · 商品类别筛选（实物 / 虚拟 / 卡券）

- **测试方法**：`should_filter_by_category_kind`
- **对应需求**：筛选「商品类别：实物商品 / 虚拟 / 卡券等类别」
- **前置**：`categoryKind = "virtual"`
- **断言**：Mapper 收到 `eq("virtual")`，SQL 用 `category_kind = ?`
- **红在哪**：`category_kind` 列不存在 → 编译红
- **陷阱**：P02 和 P03 是**两个独立维度**（类型 ≠ 类别），必须两个参数都进方法签名。一期末 shop 只有一个 `productType` 字段同时背两个概念，是 16 处缺口里唯一的「结构性」问题

---

## P04 · 状态筛选（上架 / 下架）

- **测试方法**：`should_filter_by_status`
- **对应需求**：筛选「状态：上架、下架」
- **前置**：`status = "off_sale"`
- **断言**：Mapper 收到 `eq("off_sale")`，SQL 用 `status = ?`
- **红在哪**：无实现
- **陷阱**：非法状态值（如 `"abc"`）应该**返回空列表还是忽略该条件**？建议**返回失败**，不要静默忽略 —— 静默忽略会让用户以为筛选生效了。另写一条 `should_reject_illegal_status_value`

---

## P05 · 配送方式多选组合 ★

- **测试方法**：`should_filter_by_multiple_delivery_types`
- **对应需求**：筛选「配送方式：同城配送、用户自提、快递配送等，**支持多选组合**」
- **前置**：`deliveryTypes = ["express", "self_pickup"]`
- **断言**：
  - Mapper 收到 size = 2 的集合
  - 生成的 SQL 是 `delivery_type IN (?, ?)`
  - 商品同时支持快递和自提 → 命中；只支持同城配送 → 不命中
- **红在哪**：`deliveryTypes` 参数不存在 → 编译红
- **陷阱（多选是需求里唯一强调的筛选方式）**：
  - 参数接收要能同时处理**重复参数**（`?dt=a&dt=b`）和**逗号分隔**（`?dt=a,b`）
  - SQL 用 `<foreach>` 拼 `IN`，占位符必须是 **`#{}`**，不能 `${}`（`${}` 是字符串拼接 = 注入）
  - 空集合时**整段 `IN` 不能拼出来**（`IN ()` 是语法错误，直接抛异常）
- **为什么 ★**：这是 6 个筛选项里唯一「多选」的，也是最容易实现错的一个

- **测试方法**：`should_apply_all_six_filters_together`
- **对应需求**：功能按钮「搜索：根据筛选条件查询商品列表」
- **前置**：6 个参数全部有值
- **断言**：**一次** Mapper 调用里 6 个参数都非空（`ArgumentCaptor` 捕获后逐个断言）

# 功能点 2 · 列表展示（P08~P12，5 条）

## P08 · 分页：页大小上限 + 总数正确

- **测试方法**：`should_cap_page_size_and_return_correct_total`
- **对应需求**：隐含（分页列表）
- **前置**：`size = 1000`
- **断言**：
  - 实际传给 Mapper 的 size **被压到上限**（如 100）
  - `total` 来自 `countByPage`，与 list 分开两次调用
  - offset = `(page-1) * size`
- **红在哪**：无实现
- **陷阱**：**不压上限就是 DoS 入口** —— 前端传 `size=999999` 可以把整表捞出来。这条是安全断言，不只是功能断言

## P09 · 按 sort 倒序（数字越大越靠前）

- **测试方法**：`should_sort_by_sort_field_desc`
- **对应需求**：列表「排序：数字，数字越大前台展示越靠前」
- **前置**：3 个商品 `sort = 5 / 100 / 1`
- **断言**：返回顺序为 `100 → 5 → 1`
- **红在哪**：SQL 无 `ORDER BY sort DESC` → 断言红
- **陷阱**：需求原文明确写了「**数字越大越靠前**」，所以是 **DESC**，不是 ASC。这是需求少有的把方向写死的地方，测试注释里要引用原文

## P10 · 列表 12 个字段齐备

- **测试方法**：`should_return_all_twelve_list_fields`
- **对应需求**：列表字段全清单
- **断言** 12 个字段都非空：
  ```
  mainImage, name, marketPrice, price, sales, inflatedSales,
  warehouseStock, storeStock, goodsType, categoryKind, status, deliveryTypes
  ```
- **红在哪**：缺任一字段（`inflatedSales` / `warehouseStock` / `storeStock` / `deliveryTypes` 都是一期末没有的）→ 编译红或断言红
- **陷阱**：`sort` 是第 13 个字段（需求里列了），但它是排序依据，建议一起返回方便前端调试。**断言里可以宽松点，只断言 12 个必填项**

## P11 · 真实销量与注水销量分开返回 ★

- **测试方法**：`should_return_real_and_inflated_sales_separately`
- **对应需求**：列表「商品销量：真实成交销量 / 注水销量：虚拟销量（商家可配置）」
- **前置**：`sales = 120`、`inflatedSales = 5000`
- **断言**：
  - `sales == 120`、`inflatedSales == 5000`
  - **`sales` 不等于 `120 + 5000`**（不能被合并）
- **红在哪**：只有一个 `sales` 字段 → 编译红
- **陷阱**：需求把两者分开列，说明**前台展示的可能是和，但后台必须分开**。如果实现里把注水销量加进 `sales`，商家就再也分不清真实经营数据 —— 这是数据诚信问题
- **为什么 ★**：这条测的是「字段的独立性」，只断言「两个字段都存在」不够，必须断言**值互不污染**

---

## P12 · 仓库库存与门店库存分开返回

- **测试方法**：`should_return_warehouse_and_store_stock_separately`
- **对应需求**：列表「仓库库存：中心仓库库存数量 / 门店库存：门店可售库存数量」
- **前置**：`warehouseStock = 800`、`storeStock = 35`
- **断言**：两个字段各自等于桩值，且 `warehouseStock != storeStock`（桩数据必须让两者不同）
- **红在哪**：只有一个 `stock` 字段 → 编译红
- **陷阱**：如果桩数据让两者相等（都传 100），实现即使把两个字段映射到同一个源也照样绿。**桩值必须不等**

# 功能点 3 · 删除（P13~P15，3 条）

## P13 · 已产生订单的商品禁止删除 ★★

- **测试方法**：`should_reject_delete_when_product_has_orders`
- **对应需求**：操作列「删除商品，弹出二次确认弹窗；**已产生订单的商品禁止删除**」
- **前置**：`orderItemMapper.countByProductId(5L)` → `2L`
- **断言**：
  - 返回 `code != 200`，提示含「已产生订单」
  - **`verify(productMapper, never()).deleteByIdAndShop(any(), any())`** —— 一次都没删
- **红在哪**：`countByProductId` 不存在 → 编译红
- **陷阱（关键）**：只断言「返回失败」是不够的。实现完全可以「先删了，再发现不该删，然后返回失败」。必须用 `never()` 证明**没执行删除**
- **顺序**：必须先查 `tb_order_item` 再删，**顺序反了数据就没了**
- **为什么 ★★**：这是需求原文用「禁止」二字写死的规则，也是最典型的「业务约束必须由后端守」的案例

---

## P14 · 无订单引用可正常删除

- **测试方法**：`should_allow_delete_when_product_has_no_order`
- **对应需求**：同上（反例）
- **前置**：`countByProductId(6L)` → `0L`
- **断言**：返回成功，`verify(productMapper).deleteByIdAndShop(6L, SHOP_ID)` 恰好一次
- **红在哪**：无实现
- **陷阱**：**这条必须和 P13 成对存在**。只有 P13 的话，实现写成「永远返回失败」也能绿 —— 那就把删除功能彻底废了。一正一反才是完整约束

---

## P15 · 越权：删别家商品被拒

- **测试方法**：`should_not_delete_other_shops_product`
- **对应需求**：权限段「只查看当前登录店铺数据」
- **前置**：商品 9 属于店铺 2，当前 `SHOP_ID = 1`
- **断言**：
  - `deleteByIdAndShop(9L, 1L)` 影响 0 行
  - 返回失败
  - `countByProductId` **根本没被调用**（越权应该最先拦下，不用查订单引用）
- **红在哪**：删除方法缺 `shop_id` 条件 → 断言红
- **陷阱**：越权校验要在 SQL 的 `WHERE id=? AND shop_id=?` 里，不能「先查商品再比 shopId」

# 功能点 4 · 批量设置（P16~P21，6 条）

统一返回结构：`{ total, success, failed, results[] }`，**逐条独立，一条失败不回滚其他条**。

## P16 · 批量改状态：逐条独立 ★

- **测试方法**：`should_change_status_per_item_independently`
- **对应需求**：功能按钮「批量设置：批量修改商品**状态**」
- **前置**：3 个商品 id `[1, 2, 3]`，其中 2 属于别家店铺
- **断言**：
  - `total = 3`、`success = 2`、`failed = 1`
  - 商品 1 和 3 各自 `updateStatus` 被调用一次
  - 商品 2 的 `updateStatus(2L, ...)` **影响 0 行**，结果明细里标记为失败
- **红在哪**：批量方法不存在 → 编译红
- **陷阱**：**批量操作一律不加 `@Transactional`**。整体回滚意味着「3 个里 1 个越权，另外 2 个也不改了」—— 商家点一次什么都没发生，还不知道为什么
- **为什么 ★**：这是本项目「事务边界」最容易被答辩追问的地方

---

## P17 · 一条失败不影响其余，返回失败明细

- **测试方法**：`should_report_partial_failure_without_rolling_back`
- **对应需求**：同上（结果可观测性）
- **前置**：3 个 id，第 2 个更新时抛异常
- **断言**：
  - 返回结构含 `total/success/failed/results`
  - `results` 里第 2 项带失败原因（非空字符串）
  - 第 1、3 项仍标记成功
  - **不抛异常**（异常必须被逐条 try/catch 吃掉）
- **红在哪**：无实现
- **陷阱**：**批量接口不能抛异常**。抛了前端就只看到 500，不知道哪几条成功、该重试哪几条

- **陷阱**：多选值**必须序列化后存**（`delivery_types` 是逗号分隔列）。要注意「重复值」和「空集合」：空集合表示「清空配送方式」，还是「不修改」？**建议空集合 = 清空**，并在测试里固定这个语义

# 功能点 5 · 导出 / 导入（P22~P23，2 条）

> **本批最后做**，会引入 POI / EasyExcel 依赖，拖慢前 21 条的节奏。

## P22 · 导出当前筛选结果

- **测试方法**：`should_export_current_filtered_result`
- **对应需求**：功能按钮「导出：导出**当前筛选后**的商品列表数据为 Excel 文件」
- **前置**：筛选条件 `status = "on_sale"`、`keyword = "手机"`，命中 3 条
- **断言**：
  - 导出的**行数 = 3**（不是全表 7 条）
  - 列头与列表字段一致（12 列）
  - 导出时调用的查询**带着同样的筛选条件**（`ArgumentCaptor` 断言 6 个参数）
- **红在哪**：导出方法不存在 → 编译红
- **陷阱**：
  - **"当前筛选后"是关键** —— 最常见的 bug 是导出全表
  - 分页参数要**忽略**（导出不能只导当前页 10 条）
  - 文件样式（列宽/颜色）**不测**，只测数据行数和列值

---

## P23 · 导入 Excel：按商品编码判定新增 / 更新

- **测试方法**：`should_import_by_product_code_upsert`
- **对应需求**：功能按钮「导入商品：上传 Excel 模板，批量**新增/更新**商品」
- **前置**：Excel 3 行 ——
  ```
  编码 P001（已存在）→ 应更新
  编码 P002（已存在）→ 应更新
  编码 P999（不存在）→ 应新增
  ```
- **断言**：
  - `insert` 调用 1 次（P999）
  - `update` 调用 2 次（P001、P002）
  - 返回 `{ total: 3, insert: 1, update: 2, failed: 0 }`
- **红在哪**：导入方法不存在 → 编译红
- **陷阱**：
  - **判定依据是「商品编码」（`product_code`），不是 id**。Excel 里没有数据库 id
  - 编码为空的行要跳过并计入失败，不能当新增插进去（否则会产生一堆空商品）
  - 导入的隔离同样重要：导入的商品必须强制带上当前 `shop_id`，**不能让 Excel 里的 shop_id 生效**
