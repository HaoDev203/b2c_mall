## 一、两条线互不干扰

| 模块 | 角色 | 状态 |
|---|---|---|
| `shop` | **设计模式作业**（策略 / 状态 / 模板方法 / 观察者 + 支付 / 购物车 / 认证） | **完全不动**，已定格 |
| `mall-tdd` | **本次 TDD 交付物**，从零实现需求文档 5 个页面 | 待建 |

两者物理隔离：不同模块、不同端口（8080 / 8082）、不同数据库（`shop.db` / `mall.db`）。互不引用、互不影响编译。

**为什么必须是独立模块而不是 shop 里的新包**
同一个 Spring 上下文里，`com.shop.service.DashboardService` 与 `com.mall.tdd.service.DashboardService` 会撞 Bean 名（默认都叫 `dashboardService`），`@RequestMapping("/dashboard")` 也会路径冲突。既然 shop 要保持不动，就只能拆模块。

## 三、每批的执行流程（5 步，缺一步不算完成）

**① 先写全部测试**
一个批次的所有测试方法一次写完，不写实现。此时测试类**编译不过**（引用的 Service / Mapper 方法还不存在）——这是正常的，是 RED 的一部分。

**② 跑一次，确认红在预期位置**
```bash
export JAVA_HOME=/d/jdk17
cd "/d/demo/commerce platform"
/d/maven/apache-maven-4.0.0-rc-5/bin/mvn -B -pl mall-tdd test -Duser.language=en -Duser.country=US
```
加 `-Duser.language=en` 是因为中文编译错误在 GBK 控制台会乱码。

**红的位置必须和拆解文档里每条写的「红在哪」对上**。对不上就说明测试写错了 → **改测试，不改实现**。

**③ 写最小实现**
只写让测试变绿的代码。不提前设计、不加测试没要求的功能。

**④ 全绿后再重构（TDD 第三步，最容易省掉）**
本项目的重构靶子（都有测试保护，改完必须仍全绿）：
- B5 的 `OrderQueryService.list(...)` 十几个参数 → 提取 `OrderQuery` 参数对象（Long Parameter List）
- B2 的 `DashboardService` 4 个指标计算方法重复 → 提取 `Metric` 计算模板
- B4 的 5 个批量方法 → 提取 `BatchResult` + 通用逐条执行器

**⑤ 提交两个 commit**
```bash
git add mall-tdd/src/test
git commit -m "test(mall-tdd): B1 九条验收测试（红）"

git add mall-tdd/src/main
git commit -m "feat(mall-tdd): C 端商品列表（B1）"
```

建表 / 加列单独一个 `chore` commit，**不要和 test/feat 混在一起** —— 改实体类会导致整批编译红，混在测试 commit 里会让人分不清「红是因为测试还是因为缺字段」。

## 四、答辩演示脚本（老师怎么确认这是真 TDD）

老师看 TDD 课项目，核心疑问只有一个：**「你这是先写测试，还是先写代码再补测试？」**

git 历史能证明，但要主动演示。建议按这个顺序：

**① 打开 `git log --oneline`，指出配对结构**
```
feat(mall-tdd): C 端商品列表（B1）
test(mall-tdd): B1 九条验收测试（红）
```
**test 永远在 feat 上面**（时间更早）。每批都是这个结构。

**② 现场 checkout 到某个 test commit，展示编译红**
```bash
git checkout <test-commit>
mvn -pl mall-tdd test
# → COMPILATION ERROR: cannot find symbol: method selectOnSalePage(...)
```
这一下就证明了「测试先于实现存在」。

**③ 回到最新，展示全绿 + jacoco 报告**
```bash
mvn -pl mall-tdd test jacoco:report
# → Tests run: 88, Failures: 0
# → mall-tdd/target/site/jacoco/index.html
```

**④ 挑一条最硬的现场改坏，看测试立刻红**
推荐 **D19（昨日为 0 → 100.00%）**：把它改成返回 `0`，跑测试立刻红，因为需求原文写死了 `+100.00%`。
这一下同时证明了「测试是真的在跑」和「测试钉的是需求不是实现」。

**⑤ 说明哪些是测不了的**
主动说：图标、颜色、截断、弹窗、跳转是前端职责，后端交付的是数据契约（见 `task/需求拆解-00-总览.md` §五）。**主动划边界比被问出来强**。

## 五、风险与应对

| 风险 | 表现 | 应对 |
|---|---|---|
| **假绿** | `No tests to run` + `BUILD SUCCESS` | B0 必须先跑出 `Tests run: 1`，否则不往下走 |
| **Mock 测不出 SQL 语义** | 测试全绿但 SQL 是 `LIKE` 不是 `=` | 精确匹配 / 区间 / 去重类断言配真 SQL 探针（事务内 rollback） |
| **需求有缺口** | 订单类型、订单类别没有枚举值；退款与售后没区分 | 自己定一套并写进文档，答辩时主动说「需求未给，这是我的口径」 |
| **88 条做不完** | 时间不够 | 优先级：B0 → B1 → B2 → B3，剩下两批保留拆解文档 |
| **演示数据撑不住** | 趋势图是一条平线、同比全是 100% | 补到每天 10~20 单、跨 3 天，至少覆盖 3 个时段 |
